## 2. 残留瓶颈逐条分析

### 🔴 P0-A 三个 computed 在大图频繁全量重建

**位置**：
- `stores/ruleEngine.ts:141-152` (connectedHandleIndex)
- `stores/ruleEngine.ts:173-179` (nodeById)
- `stores/ruleEngine.ts:203-224` (baseLodLevelMap)

**问题**：
所有三个 computed 都依赖 `nodes.value` / `edges.value` 的**整体引用**，每次 `nodes.value = newArr` 或 `edges.value = newArr` 触发都全量重建：

```ts
const nodeById = computed(() => {
  const map = new Map()
  for (const n of nodes.value) map.set(n.id, n)  // 200 节点 200 次 set
  return map
})

const connectedHandleIndex = computed(() => {
  const index = new Set()
  for (const e of edges.value) {                  // 200 条边 400 次 add
    if (e.sourceHandle) index.add(`${e.source}:${e.sourceHandle}:source`)
    if (e.targetHandle) index.add(`${e.target}:${e.targetHandle}:target`)
  }
  return index
})

const baseLodLevelMap = computed(() => {
  const map = new Map()
  const baseLod = viewportZoom.value < 0.5 ? 0 : 1
  for (const n of nodes.value) map.set(n.id, baseLod)  // 200 节点 200 次 set
  return map
})
```

**触发路径（高频）**：

| 路径 | 频率 | 影响的 computed |
|------|----|---|
| `setViewportZoom(zoom)` 缩放 | 16ms 一次 (rAF 节流后) | `baseLodLevelMap` |
| `addEdge` / `removeEdge` 连线 | 每次操作 | `connectedHandleIndex` |
| `saveHistory` 触发 `edges.value = [...]` | 每次操作 | `connectedHandleIndex` |
| `handleSelectionEnd` 触发 `nodes.value = [...]` | 每次框选结束 | `nodeById` + `baseLodLevelMap` |
| `handlePaneClick` 触发 `nodes.value = [...]` | 每次空白点击 | 同上 |
| `triggerRef(nodes)` (drag-stop) | 每次拖动结束 | 同上 |

**爆点**：缩放 60Hz × 200 节点 Map 重建 = 12000 ops/秒 + 每次 GC pressure。LOD-1 锁定逻辑（`isLodLocked`）只在 drag/selection 期间生效，**纯缩放时仍每帧重建**。

**根因**：computed 没有"输入未变化时短路"机制，Vue3 reactivity 只能比较顶层引用。

**修复方案**：

```ts
// === 方案 1: baseLodLevelMap 缓存 baseLod，跨阈值才重建 ===
let cachedBaseLod: 0 | 1 | null = null
let cachedNodesRef: Node<RuleNodeData>[] | null = null
let cachedMap: Map<string, 0 | 1> = new Map()

const baseLodLevelMap = computed(() => {
  const zoom = viewportZoom.value
  const baseLod: 0 | 1 = zoom < 0.5 ? 0 : 1
  const nodesRef = nodes.value

  // 关键短路: baseLod 未跨阈值 + nodes 数组引用未变 → 复用上次 Map
  if (cachedBaseLod === baseLod && cachedNodesRef === nodesRef) {
    return cachedMap
  }

  // 否则重建
  const map = new Map<string, 0 | 1>()
  for (const n of nodesRef) map.set(n.id, baseLod)
  cachedBaseLod = baseLod
  cachedNodesRef = nodesRef
  cachedMap = map
  return map
})

// === 方案 2: nodeById / connectedHandleIndex 同样模式 ===
// nodeById 只在 nodes.value 数组引用变化时重建 (已自动)，但
// 拖动期间 triggerRef(nodes) 也会让它重算 — 改为弱引用 + nodes.length 哈希校验

// === 方案 3 (更激进): 改为手动维护的 Map (非 computed) ===
// 在 createNode/removeNode/loadGraph 中显式增删 Map，
// 摆脱 Vue reactivity 全量重建。改动较大但收益最高。
```

**推荐**：方案 1 (`baseLodLevelMap` 短路) — 改 5 行命中 60Hz 热点，立刻消除缩放期间的 Map 重建。`nodeById` / `connectedHandleIndex` 收益较低（变化频率低）暂不动。

**预期收益**：缩放期间 60Hz × 200 节点 Map.set → 0 次 → 帧耗 -1.5ms。

### 🔴 P0-B 选中态切换全图触发 VueFlow diff

**位置**：
- `RuleCanvas.vue:1361-1364` (handleSelectionEnd)
- `RuleCanvas.vue:1581-1585` (handlePaneClick)
- `RuleCanvas.vue:1300-1306` (handlePaste)
- `RuleCanvas.vue:1224-1227` (handleCut)

**问题**：
这些路径都用 `store.nodes = [...(store.nodes as any)]` **重建数组引用**触发 VueFlow 内部 useVModel 浅 watch。VueFlow 检测到 props.nodes 引用变 → 触发 `createGraphNodes` → **80 节点全部重新构造 reactive GraphNode + 重算 80 边 path**。

```ts
// handleSelectionEnd
function handleSelectionEnd() {
  // ... 同步 selected 状态到 store.nodes[i].selected ...
  if (changed) {
    store.nodes = [...(store.nodes as any)] as any  // ← 触发整图重建
  }
}

// handlePaneClick
function handlePaneClick() {
  for (const n of store.nodes as any[]) n.selected = false
  store.selectNode(null)
  store.nodes = [...(store.nodes as any)] as any  // ← 同上
}
```

**根因**：
P0-1 优化（drag-stop 走 `triggerRef(nodes)` 而非数组替换）已经证明 **shallow watch 用 `triggerRef` 通知就够，不需要替换数组引用**。但选中态变更未沿用这条路径，仍走老路。

**测试印证**：drag-stop 200 节点测试 ~15ms，框选结束 200 节点测试 ~120ms（同样 N，时间 8 倍差） — 差距正是 VueFlow `createGraphNodes` 全量重建。

**修复**：
```ts
// 改 handleSelectionEnd / handlePaneClick / handleCut 全部走 triggerRef
function handleSelectionEnd() {
  // ... mutate n.selected ...
  if (changed) {
    triggerRef(nodes)  // ← 替换数组重建
  }
}
```

但**注意**：VueFlow 内部 `useVModel` 浅 watch 实际是这样工作的：
- 数组引用变 → 触发 watch → `createGraphNodes`
- 数组引用不变 + `triggerRef` → 触发 watch → 但 VueFlow 内部 `applyChanges` 不会触发，因为 props.nodes 引用未变

如果 VueFlow 1.48 的 watch 是浅比较（`watch(() => props.nodes)`），`triggerRef` 不会触发它（因为浅比较看引用）。需要实测验证：用 Vue DevTools 监听这条 watch 是否触发。

**回退方案**：如果 `triggerRef` 不行，至少把 selected 同步聚合到一次 `nextTick` 微任务里 + 用 `requestIdleCallback` 推迟非紧急的视觉同步。

**预期收益**：100 节点框选结束帧耗 -50%（120ms → 60ms 或更低）。

### 🔴 P0-C useCogniFlowDrag DOM 遍历挂 d3-drag handler

**位置**：`composables/useCogniFlowDrag.ts:93-107` + `309-316`

**问题**：
当前实现是 **每个节点 wrapper DOM 上挂 d3-drag handler**，通过 `watch(store.nodes)` + `setTimeout` 多次重试同步：

```ts
function syncDragHandlers() {
  const els = document.querySelectorAll<HTMLElement>('.vue-flow__node')
  // diff installedMap，挂载新增/卸载移除
  // 每节点都要 d3Select(el).call(dragHandler)
}

watch(() => store.nodes, () => {
  nextTick(() => syncDragHandlers())
  setTimeout(() => syncDragHandlers(), 100)  // 双重保险
})

onMounted(() => {
  nextTick(() => syncDragHandlers())
  setTimeout(() => syncDragHandlers(), 0)
  setTimeout(() => syncDragHandlers(), 100)
  setTimeout(() => syncDragHandlers(), 500)  // 4 次重试
})
```

**问题分析**：
1. **scaling problem**：100 节点画布 → 100 个 d3-drag handler，每个 handler 闭包占内存 ~1KB → 100KB 内存 + 100 个事件监听器
2. **同步竞态**：节点增删 → watch 触发 → 但 DOM 还没更新 → 重试 4 次 + 100ms 后再补一次，时序脆弱
3. **粘贴/加载**：加载 100 节点 → 100 次 `installOnNode` → 100 次 d3Select + 100 次事件绑定 → ~30ms 阻塞
4. **`only-render-visible-elements="true"` 时不生效**：视口外节点没有 DOM，`querySelectorAll` 找不到 → 滚动到视口后才挂载 → 拖动可能首次失效

**修复方案：事件委托**

```ts
// useCogniFlowDrag.ts 重构: 单一 handler 挂在 vue-flow__viewport
function setupDelegatedDrag() {
  const viewport = document.querySelector('.vue-flow__viewport')
  if (!viewport) return

  d3Select(viewport).call(
    d3Drag<HTMLElement, unknown>()
      .filter((event: MouseEvent) => {
        // 通过 event.target.closest('.vue-flow__node[data-id]') 找节点
        const nodeEl = (event.target as HTMLElement)?.closest<HTMLElement>('.vue-flow__node[data-id]')
        if (!nodeEl) return false
        if ((event.target as HTMLElement)?.closest('.nodrag, .vue-flow__handle, .vue-flow__edge, .node-expand-btn')) return false
        // 把 nodeEl 存到 event.subject 供后续 on('start') 用
        ;(event as any).__cfNodeEl = nodeEl
        return true
      })
      .on('start', (event) => onDragStart(event, (event.sourceEvent as any).__cfNodeEl))
      .on('drag', (event) => onDrag(event, (event.sourceEvent as any).__cfNodeEl))
      .on('end', (event) => onDragEnd(event, (event.sourceEvent as any).__cfNodeEl))
  )
}

// 删掉所有 syncDragHandlers / watch / setTimeout 重试链
onMounted(() => nextTick(setupDelegatedDrag))
```

**预期收益**：
- 200 节点初始化 d3-drag 开销 ~60ms → 1ms (单一 handler)
- 内存占用 200 节点 ~200KB → ~1KB
- 视口外节点拖动可用性 100% (任何被渲染出 DOM 的节点都能拖)
- 删 ~50 行重试同步代码

**风险**：
- d3-drag 在 viewport 容器上 capture 模式可能与 VueFlow 内部事件冲突 → 需 isolation 测试 (Handle 拖连线 / 框选)
- `closest('.vue-flow__node[data-id]')` 每次 mousedown 一次 DOM 遍历，但只在 mousedown 一帧执行，开销极低

### 🔴 P0-D handleNodesChange 用 nodes.value.find 而非 nodeById

**位置**：`RuleCanvas.vue:1714`

```ts
for (const c of positionChanges) {
  const node = nodes.value.find(n => n.id === c.id)  // ← O(N) 查找
  if (node && c.position) {
    node.position = c.position
  }
}
```

**问题**：drag-stop 多节点拖动 → `positionChanges.length = K`，每个查 O(N) → O(K×N)。100 节点全选拖动 → 100 × 100 = 10000 次属性比较。

**修复**：改用 store 的 `nodeById` Map (O(1))：

```ts
for (const c of positionChanges) {
  const node = store.nodeById.get(c.id)  // ← O(1)
  if (node && c.position) {
    node.position = c.position
  }
}
```

**预期收益**：100 节点全选拖动结束帧耗 ~10ms → ~1ms (O(K×N) → O(K))。

**注意**：访问 `store.nodeById.get` 触发 computed 重建（见 P0-A），需先做 P0-A 的短路缓存或确保 `nodeById` 在 drag-stop 时是干净状态（不被 dragging 锁定）。

### 🟡 P1-E userSelectionRect watch 60Hz 浅复制

### 🟡 P1-F connectedHandleIndex 全量重建无增量

**位置**：`stores/ruleEngine.ts:141-152`

**问题**：当前每次 edges 数组变化（无论 push/filter/replace）都全量遍历重建 Set。100 边 × 每次连线/删边一次 = 几十毫秒。

**修复（增量维护）**：
```ts
// 改为手动维护 Set + 在 addEdge/removeEdge/loadGraph 显式更新
const _connectedHandleIndex = new Set<string>()
const connectedHandleIndex = readonly(_connectedHandleIndex)  // 暴露只读

function addEdge(connection) {
  const e = { ... }
  edges.value = [...edges.value, e]
  if (e.sourceHandle) _connectedHandleIndex.add(`${e.source}:${e.sourceHandle}:source`)
  if (e.targetHandle) _connectedHandleIndex.add(`${e.target}:${e.targetHandle}:target`)
  triggerRef(connectedHandleIndex)  // 通知依赖
  saveHistory()
}

function removeEdge(edgeId) {
  const e = edges.value.find(x => x.id === edgeId)
  if (e?.sourceHandle) _connectedHandleIndex.delete(`${e.source}:${e.sourceHandle}:source`)
  if (e?.targetHandle) _connectedHandleIndex.delete(`${e.target}:${e.targetHandle}:target`)
  edges.value = edges.value.filter(x => x.id !== edgeId)
  triggerRef(connectedHandleIndex)
  saveHistory()
}

function loadGraph(...) {
  // ... 解析 edges ...
  _connectedHandleIndex.clear()
  for (const e of edges.value) {
    if (e.sourceHandle) _connectedHandleIndex.add(`${e.source}:${e.sourceHandle}:source`)
    if (e.targetHandle) _connectedHandleIndex.add(`${e.target}:${e.targetHandle}:target`)
  }
  triggerRef(connectedHandleIndex)
}
```

**预期收益**：连线/删边操作的 set 重建从 O(E) → O(1)。

**风险**：增量维护引入状态一致性问题 — `removeNodes` 批量删除时要 sync 多条边的索引清理。

### 🟡 P1-G 复制粘贴节点 JSON.parse(JSON.stringify(...)) 开销

**位置**：`RuleCanvas.vue:1197, 1217, 1268`

```ts
clipboard.value = {
  nodes: selected.map((n: any) => JSON.parse(JSON.stringify(n))),  // ← 每节点单独 parse
  ...
}

// ...

const newNodes = srcNodes.map((n: any) => {
  const cloned = JSON.parse(JSON.stringify(n))  // ← 再次 parse
  return { ...cloned, id: newNodeId, position: { ... } }
})
```

**问题**：
1. 每节点单独 stringify+parse，N 节点 N 次 — 应一次 stringify 整个数组
2. 复制时存的就是已序列化数据，粘贴时**又拷贝一次**，2N 次开销
3. 100 节点复制粘贴 ~150ms 阻塞

**修复**：
```ts
// 复制: 一次性 stringify
clipboard.value = {
  nodesJson: JSON.stringify(selected),  // 1 次 stringify N 节点
  edgesJson: JSON.stringify(relatedEdges),
  mousePos: getSelectionBboxCenter(),
}

// 粘贴: 一次性 parse + map
const srcNodes = JSON.parse(clipboard.value.nodesJson)  // 1 次 parse
const newNodes = srcNodes.map((n: any) => ({ ...n, id: newId(), position: { ... }, selected: true }))
```

**或更优**：用 `structuredClone(selected)` (JSON 1.5~3x 快，原生 deep clone)。先前 Phase 15 试过 structuredClone 在 history 上失败（VueFlow 节点含 DOM 引用），但这里是已经 strip 过 DOM 引用的节点 wrapper data，应该可用。

**预期收益**：100 节点复制粘贴 ~150ms → ~30ms (5x 改善)。

### 🟡 P1-H executionLogs 性能与无虚拟滚动

**位置**：
- `stores/ruleEngine.ts:98-104` (`executionState: ref({...})`)
- `RuleCanvas.vue:549-572` (`v-for in executionLogs`)

**问题 1**：`executionState` 是 `ref` (深代理) → `logs` 数组 push 触发深 watcher。日志高速推送（YOLO 触发器 30 FPS 推流场景下）会成为新瓶颈。

**问题 2**：`<div v-for="log in executionLogs">` 没有虚拟滚动，1000+ 日志后面板滚动会卡。

**修复**：
```ts
// 1. 改 shallowRef + mutable logs array
const executionState = shallowRef<ExecutionState>({
  status: 'idle', progress: 0, executionId: null, logs: [], nodeStates: {}
})
function addExecutionLog(log) {
  executionState.value.logs.push(log)
  triggerRef(executionState)  // 手动通知
}

// 2. throttle 批量合并 100ms
const pendingLogs: Log[] = []
let logsRafId = 0
function addExecutionLogBatched(log) {
  pendingLogs.push(log)
  if (!logsRafId) {
    logsRafId = setTimeout(() => {
      executionState.value.logs.push(...pendingLogs)
      pendingLogs.length = 0
      logsRafId = 0
      triggerRef(executionState)
    }, 100) as any
  }
}

// 3. 虚拟滚动: 用 vue-virtual-scroller 或 element-plus el-virtual-list
<el-virtual-list :data="executionLogs" :height="200" :item-size="32">
  <template #default="{ item }"><LogEntry :log="item" /></template>
</el-virtual-list>
```

**预期收益**：千行日志滚动 60fps，日志推送峰值 fps 不掉。

### 🟢 P2-I 节点 hover transition 在小图（< 80）未关闭

**位置**：`RuleNode.vue:184`

```scss
.rule-node {
  transition: border-color 0.15s ease, box-shadow 0.15s ease;
}
```

**问题**：执行期 60Hz 节点状态切换（idle → running → success）会触发 transition 动画，每个节点单独 GPU 合成层，但 transition 期间浏览器仍要 schedule paint。50 节点同时跳到 success 时帧耗增加 ~5ms。

**修复**：状态切换瞬间禁用 transition：
```scss
.rule-node[data-status='running'],
.rule-node[data-status='success'],
.rule-node[data-status='failed'] {
  transition: none;  // 状态变化时不补间，立即生效
}
.rule-node[data-status='idle'] {
  transition: border-color 0.15s ease, box-shadow 0.15s ease;
}
```

或者**完全去掉 hover transition**（设计取舍，不影响性能感知）。

**预期收益**：执行期 50 节点状态广播 -3~5ms。

### 3.1 现状

```vue
<!-- 缩放期间禁用视口裁剪 (用户感知不到，因为节点都在 GPU 合成层一起 transform) -->
<VueFlow :only-render-visible-elements="!isZooming" />
```

**预期收益**：极致缩放体验 → 200 节点画布缩放 50→55fps。

## 5. 加载 / 保存专项

### 5.1 现状
- ✅ 缩略图 `requestIdleCallback` 异步
- ✅ markRaw + shallowRef 阻止节点 deep proxy

### 5.2 残留问题

**问题 1**：`loadGraph` 一次性 `JSON.parse` + `map` 200 节点 + `markRaw` 阻塞 ~50~80ms。

**修复**：分批解析 (chunked) — 每帧解析 50 节点 + rAF 让出主线程。或者 Web Worker 中解析 + 主线程 markRaw + 写入 store。

```ts
async function loadGraph(id: number) {
  const res = await ruleEngineApi.getGraphDetail(id)
  const data = res.data
  graphMeta.value = { ... }

  // 分批 mount 节点
  const allNodes = data.nodes ?? []
  const CHUNK_SIZE = 50
  const result: Node<RuleNodeData>[] = []
  for (let i = 0; i < allNodes.length; i += CHUNK_SIZE) {
    const chunk = allNodes.slice(i, i + CHUNK_SIZE).map((n: GraphNode) => markRaw({ ... }))
    result.push(...chunk)
    nodes.value = [...result]  // 渐进式渲染
    await new Promise(r => requestAnimationFrame(r))  // 让出主线程
  }
}
```

**问题 2**：`saveGraph` 序列化时 `JSON.stringify(nodes.value.map(n => ({ ... })))` 200 节点 ~50ms 阻塞。

**修复**：在 `requestIdleCallback` 中做序列化 + HTTP POST。或者后端改为接收 binary protobuf 格式（重大改动，搁置）。

## 7. 框选专项（已优化但仍有空间）

### 7.1 现状
- ✅ VueFlow Fork: `Pane.onPointerUp` 不重复算
- ✅ `select-nodes-on-drag="false"`
- ✅ `isBatchDragging` 标志拦截 60Hz nodesChange
- ✅ `cachedSelectionRect` watch 修复时序

### 7.2 残留问题

**问题 1**：`onPointerMove` 仍 60Hz × O(N) 视口节点的 `getNodesInside` 包围盒检测 → 200 节点框选时 12000 ops/秒。

**修复方案（远期）**：空间索引 (R-tree / quadtree)。VueFlow 1.48 没内置，需 fork。
- **R-tree** (`rbush` 库) 增删 O(log N)，查询 O(log N + k)
- 200 节点框选 60Hz × O(log N + k) ~ 60Hz × 10~20 = 1200 ops/秒（10x 改善）

**搁置评估**：复杂度高、维护性差。除非 100+ 节点画布成为常态，否则不建议。

**问题 2**：框选过程节点 selected class 通过 VueFlow 内部 `applyNodeChanges` 添加。100 节点全部框选 → VueFlow 内部 `nodes.value.map(n => ({ ...n, selected: true }))` → 整图重建 → 触发我们 `handleNodesChange` (哪怕 `isBatchDragging` 拦截) → `applyVueFlowNodeChanges` 仍 O(N) 应用。

**修复**：加 `isBatchDragging` 期间 `applyVueFlowNodeChanges` 也跳过（已有，确认无回退）。

## 11. 总结

1. **响应式系统的最后一公里**：computed 短路、triggerRef 替代数组重建（P0-A、P0-B、P0-D）
