# 规则引擎大规模节点画布架构方案

**日期**: 2026-06-07
**范围**: WebUI 规则引擎画布 (`RuleCanvas.vue` / `RuleNode.vue` / `ruleEngine.ts`)
**目标**: 支持 200-500 个规则节点的可浏览、可编辑、可保存体验

---

## 1. 背景与结论

当前 WebUI 规则引擎画布已经完成一轮拖拽性能优化，包括：

| 已完成优化 | 作用 |
| --- | --- |
| VueFlow manual control | 避免拖拽中 `v-model:nodes` 每帧回写整图 |
| `nodes` / `edges` 使用 `shallowRef` | 降低 Vue 深响应式代理成本 |
| 拖拽中跳过 position 写回 | 避免 60Hz store 更新 |
| `only-render-visible-elements` | 只渲染视口内节点 |
| RuleNode 根与字段级 `v-memo` | 降低重复渲染 |
| MiniMap 拖拽期间暂停渲染 | 避免缩略图全量节点更新 |

这些优化能改善 30-80 节点的交互，但不足以让几百个复杂规则节点长期流畅。原因不是单个 bug，而是当前设计把“节点配置表单”直接放在画布节点内部，导致每个节点都是重型 Vue + Element Plus 组件。

**核心结论**:

当前设计适合中小规模规则图，不适合几百个完整可编辑节点同时在画布中渲染。要支持 200-500 节点，需要从“重型节点编辑器”改为“轻量节点壳 + 侧边属性面板 + 大图性能模式 + 增量状态管理”。

---

## 2. 目标与非目标

### 2.1 目标

| 目标 | 指标 |
| --- | --- |
| 100 节点正常编辑 | 单节点拖拽接近 60fps，明显无卡顿 |
| 200 节点可用 | 拖拽、缩放、平移、框选不卡死 |
| 500 节点可浏览 | 能打开、定位、搜索、分组查看，不要求所有节点同时精细编辑 |
| 配置编辑稳定 | 节点配置修改只影响当前节点，不触发全图组件更新 |
| 历史记录可控 | 撤销/重做不再每次深克隆整图 |

### 2.2 非目标

| 非目标 | 说明 |
| --- | --- |
| 不追求 500 个复杂表单节点同时可见 | 浏览器 DOM 和 Element Plus 组件成本不现实 |
| 不立即替换 VueFlow | 先利用 VueFlow 现有能力，避免大规模迁移风险 |
| 不做后端执行引擎改造 | 本方案只处理 WebUI 编辑体验 |
| 不一次性完成所有阶段 | 先解决节点渲染和响应式热路径 |

## 3. 当前瓶颈

### 3.1 节点组件过重

当前 `RuleNode.vue` 同时承担四类职责：

| 职责 | 当前实现 | 问题 |
| --- | --- | --- |
| 节点视觉 | 标题、类型、状态、端口 | 合理 |
| 配置编辑 | `el-input` / `el-select` / `el-slider` / `el-checkbox` 等 | 组件数量随节点数线性增长 |
| 变量绑定 | 变量按钮、菜单、输入框 ref | 每个节点维护独立交互状态 |
| 连接状态 | 每个节点扫描 `store.edges` | 边多时重复计算 |

几百节点时，即使视口虚拟化只渲染部分节点，只要视口内有几十个节点，Element Plus 控件、tooltip、select、textarea、slider 仍会带来明显渲染压力。

### 3.2 画布节点和配置编辑耦合

节点配置写入路径目前是：

```text
RuleNode widget
  -> store.updateNodeConfig()
  -> triggerRef(nodes)
  -> RuleCanvas / VueFlow / 可见 RuleNode 响应
```

即使已经用 `v-memo` 降低了重复渲染，配置字段仍然在画布节点内部，无法从根本上降低节点复杂度。

### 3.3 连接状态重复扫描

当前每个 `RuleNode` 内部都有类似逻辑：

```text
connectedHandleIds = computed(() => scan(store.edges))
```

当可见节点数为 V、边数为 E 时，连接状态计算近似为 `O(V * E)`。几百节点通常意味着几百条边，这条路径会成为持续性成本。

### 3.4 历史记录和复制粘贴是整图模型

当前历史记录通过快照保存节点和边：

```text
historyStack.push({
  nodes: cloneForHistory(nodes),
  edges: cloneForHistory(edges)
})
```

这对几十节点可接受，但几百节点时，每次创建、删除、连接、粘贴都会产生较大 JSON clone 和 GC 压力。

### 3.5 大图缺少导航型能力

几百节点规则图不能只依赖缩放和平移。需要搜索、分组、折叠、局部聚焦、子图入口，否则即使性能足够，用户也难以维护。

## 4. 推荐架构

### 4.0 Blender 对比与设计修正

Blender 的节点编辑器确实把许多输入项直接放在节点上，但它能支撑大图的原因和当前 WebUI 不同：

| Blender 做法 | 对性能的影响 |
| --- | --- |
| 原生 C/C++ UI 绘制，不是浏览器 DOM | 没有 Vue 组件、DOM diff、Element Plus 子组件成本 |
| 节点控件是轻量即时模式控件 | 输入框、数值框、开关不是复杂组件树 |
| 画布只绘制可见区域 | 视口外节点不会持续参与绘制 |
| 节点支持折叠、隐藏未连接 socket、节点组 | 大图天然通过层级和折叠降低复杂度 |
| 节点内只放常用/暴露参数 | 复杂属性仍可通过侧栏、Modifier、属性面板等位置管理 |
| 执行数据和 UI 绘制分离 | 节点求值不会让 UI 状态大面积响应式更新 |

因此，本项目不应该简单理解为“节点上不能有输入项”。更准确的结论是：

```text
节点上可以保留 Blender 风格的轻量快速输入，
但不能在每个节点里长期挂载完整 Element Plus 表单组件树。
```

推荐从“全部移到属性面板”修正为“混合式编辑”：

| 参数类型 | 推荐位置 |
| --- | --- |
| 高频、简单、短字段 | 节点内轻量控件 |
| 布尔开关、数值阈值、短枚举 | 节点内轻量控件 |
| 模型选择、文件选择、多选类别、长文本、变量绑定 | 右侧属性面板 |
| 高级配置、调试参数、执行策略 | 右侧属性面板 |
| 大图模式下所有控件 | 默认折叠，仅选中节点或展开节点渲染 |

这更接近 Blender 的真实设计：节点内保留“快速调参”，属性面板承载“完整配置”。

### 4.1 总体结构

```text
┌─────────────────────────────────────────────────────────────┐
│ RuleCanvas.vue                                               │
│                                                             │
│  ┌───────────────────────┐    ┌──────────────────────────┐  │
│  │ VueFlow Canvas         │    │ PropertiesPanel          │  │
│  │                       │    │                          │  │
│  │ LightweightRuleNode   │ -> │ NodeConfigEditor         │  │
│  │ only visual shell     │    │ Element Plus widgets     │  │
│  │ no config widgets     │    │ only selected node       │  │
│  └───────────────────────┘    └──────────────────────────┘  │
│                                                             │
│  ┌────────────────────────────────────────────────────────┐ │
│  │ LargeGraphMode                                         │ │
│  │ minimap off / shadows reduced / edge labels hidden     │ │
│  └────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ Pinia ruleEngine store                                      │
│                                                             │
│ nodes / edges                                                │
│ selectedNodeId                                               │
│ connectedHandleIndex: Set<string>                            │
│ history: command log + periodic snapshots                    │
└─────────────────────────────────────────────────────────────┘
```

核心变化：

| 改造点 | 改造前 | 改造后 |
| --- | --- | --- |
| 节点组件 | 节点内直接渲染完整配置表单 | 节点显示轻量壳 + 少量快速输入 |
| 配置编辑 | 每个节点都有 Element Plus 控件 | 右侧属性面板渲染完整控件，节点只渲染轻量 quick controls |
| 连接状态 | 每个节点扫描全部边 | Store 维护全局连接索引，节点 O(1) 查询 |
| 大图策略 | 所有图同一渲染模式 | 超过阈值自动进入性能模式 |
| 历史记录 | 每步整图快照 | 操作日志 + 周期快照 |

## 5. 详细设计

### 5.1 轻量节点壳与快速输入

新增或改造 `RuleNode.vue` 为轻量节点壳，默认只保留：

| 保留内容 | 说明 |
| --- | --- |
| 节点标题 | `data.label` / `data.type` |
| 分类图标 | 输入、检测、处理、动作、逻辑、输出 |
| 执行状态 | idle / running / success / failed / timeout |
| 输入输出端口 | Handle + 简短 label |
| 配置摘要 | 最多 1-2 行关键字段摘要，可选 |
| 快速输入 | 少量轻量控件，限制数量和类型 |

节点内快速输入规则：

| 允许在节点内 | 不建议在节点内 |
| --- | --- |
| `number` 阈值 | `model-select` |
| `toggle` / `checkbox` | `file-picker` |
| 短 `dropdown` | `multiselect` |
| 1 行短文本 | `textarea` / `code` |
| 最多 3 个 quick controls | 变量绑定菜单 |

迁移到属性面板：

| 移出节点内容 | 迁移位置 |
| --- | --- |
| 完整 `el-input` / `el-select` / `el-slider` / `el-checkbox` 表单 | 右侧 `NodeConfigEditor.vue` |
| 变量绑定按钮和菜单 | 右侧属性面板 |
| 文件选择器 | 右侧属性面板 |
| 模型选择器 | 右侧属性面板 |
| 输入框 ref / 光标插入逻辑 | 右侧属性面板 |

建议节点模板结构：

```vue
<template>
  <div class="rule-node-shell" :data-status="data.status">
    <header class="node-header">
      <SvgIcon :name="categoryIcon" />
      <span class="node-title">{{ data.label }}</span>
    </header>

    <section class="node-summary" v-if="summary">
      {{ summary }}
    </section>

    <section class="node-quick-controls" v-if="quickControls.length && !largeGraphMode">
      <!-- custom lightweight controls, not Element Plus -->
    </section>

    <section class="node-ports">
      <!-- input/output handles -->
    </section>
  </div>
</template>
```

预期收益：

| 指标 | 当前 | 改造后 |
| --- | --- | --- |
| 每节点 Element Plus 控件 | 0-6 个 | 0 个 |
| 每节点轻量 quick controls | 不受控 | 0-3 个 |
| 每节点交互状态 | 多个 ref / computed | 少量 computed |
| 可见 30 节点 DOM 压力 | 高 | 中低 |

### 5.2 右侧属性面板

新增 `NodeConfigEditor.vue`，接管所有配置控件。

输入：

```ts
interface NodeConfigEditorProps {
  nodeId: string
  data: RuleNodeData
}
```

职责：

| 职责 | 说明 |
| --- | --- |
| 根据 `configSchema` 渲染控件 | 保留现有 widget 能力 |
| 调用 `store.updateNodeConfig()` | 保持单源 store |
| 处理变量绑定 | 光标插入、变量菜单、格式校验 |
| 处理模型选择 | `availableModels` / 类别加载 |
| 处理文件选择 | file-picker |

`RuleCanvas.vue` 右侧属性区域只渲染当前选中节点：

```vue
<NodeConfigEditor
  v-if="selectedNode"
  :node-id="selectedNode.id"
  :data="selectedNode.data"
/>
```

这样几百节点时，配置控件数量始终约等于“一个节点”的控件数量。

### 5.3 连接状态索引

在 `ruleEngine.ts` 中新增连接索引：

```ts
const connectedHandleIndex = computed(() => {
  const index = new Set<string>()
  for (const edge of edges.value) {
    if (edge.sourceHandle) {
      index.add(`${edge.source}:${edge.sourceHandle}:source`)
    }
    if (edge.targetHandle) {
      index.add(`${edge.target}:${edge.targetHandle}:target`)
    }
  }
  return index
})
```

节点内查询改为：

```ts
function isHandleConnected(nodeId: string, handleId: string, direction: 'source' | 'target') {
  return store.connectedHandleIndex.has(`${nodeId}:${handleId}:${direction}`)
}
```

收益：

| 当前 | 改造后 |
| --- | --- |
| 每个可见节点扫描全部边 | Store 对边集合统一计算一次 |
| `O(V * E)` | `O(E + V * H)` |

其中 V 是可见节点数，E 是边数，H 是每个节点 handle 数。

### 5.4 大图性能模式

新增 `largeGraphMode`：

```ts
const LARGE_GRAPH_NODE_THRESHOLD = 80
const HUGE_GRAPH_NODE_THRESHOLD = 200

const largeGraphMode = computed(() => nodes.value.length >= LARGE_GRAPH_NODE_THRESHOLD)
const hugeGraphMode = computed(() => nodes.value.length >= HUGE_GRAPH_NODE_THRESHOLD)
```

大图模式策略：

| 策略 | 触发 |
| --- | --- |
| MiniMap 默认关闭 | `nodes.length >= 80` |
| 拖拽中关闭 MiniMap | 所有规模 |
| 隐藏边 label / 动画 | `nodes.length >= 80` |
| 降低节点阴影和状态 glow | `nodes.length >= 80` |
| 节点摘要折叠 | `nodes.length >= 200` |
| 提示用户使用搜索/分组 | `nodes.length >= 200` |

注意：大图模式不应该破坏用户显式设置。建议区分“系统自动关闭”和“用户手动打开”：

```ts
const minimapPreference = ref<'auto' | 'on' | 'off'>('auto')
const shouldShowMiniMap = computed(() => {
  if (isNodeDragging.value || isSelectionDragging.value) return false
  if (minimapPreference.value === 'on') return true
  if (minimapPreference.value === 'off') return false
  return !largeGraphMode.value
})
```

### 5.5 历史记录改造

当前历史记录是整图快照，建议改成操作日志为主、周期快照为辅。

操作类型：

```ts
type GraphCommand =
  | { type: 'node:create'; node: Node }
  | { type: 'node:delete'; node: Node; relatedEdges: Edge[] }
  | { type: 'node:move'; nodeId: string; from: XYPosition; to: XYPosition }
  | { type: 'node:update-config'; nodeId: string; key: string; from: unknown; to: unknown }
  | { type: 'edge:create'; edge: Edge }
  | { type: 'edge:delete'; edge: Edge }
  | { type: 'batch'; commands: GraphCommand[] }
```

历史结构：

```ts
interface HistoryState {
  checkpoints: Array<{ index: number; nodes: Node[]; edges: Edge[] }>
  commands: GraphCommand[]
  cursor: number
}
```

策略：

| 策略 | 说明 |
| --- | --- |
| 普通操作记录 command | 避免整图克隆 |
| 每 20-30 步保存 checkpoint | 避免 undo 很多步时重放过长 |
| 拖拽只记录 start/end | 不记录中间帧 |
| 批量粘贴/删除记录 batch | 保证撤销语义完整 |

阶段 1 可先保留快照历史；阶段 3 再改命令历史。

### 5.6 大图导航能力

几百节点需要导航辅助，否则性能达标也难维护。

推荐新增能力：

| 能力 | 说明 |
| --- | --- |
| 节点搜索 | 按名称、类型、分类、配置关键字搜索 |
| 定位节点 | 搜索结果点击后 `setCenter()` |
| 分类筛选 | 只突出或只显示某类节点 |
| 折叠分组 | 将局部链路折叠成 group/subgraph |
| 依赖邻域查看 | 只突出当前节点上下游 N 层 |

优先级最高的是搜索定位和上下游突出，投入小、收益高。

## 5.7 节点 LOD 与延迟激活渲染

用户提出的“把所有节点先渲染成简化 DOM 或图片，只有需要编辑时恢复成重型组件”是可行的，而且适合本项目。该方案可定义为 **节点 LOD（Level of Detail）/ 延迟激活渲染**。

核心思想：

```text
大多数节点只负责展示结构
少数激活节点才挂载交互组件
远距离或大图模式下进一步降级为极简 DOM 或图片
```

这比“所有配置都移到右侧属性面板”更接近 Blender 思路：节点仍然能表达关键信息，但不会让每个节点长期挂载重型组件。

### 5.7.1 LOD 分级

| LOD | 形态 | 使用场景 | 内容 |
| --- | --- | --- | --- |
| LOD 0 | 极简节点 | 远距离缩放、200+ 节点大图 | 类型色条、标题缩略、状态点、端口点 |
| LOD 1 | 轻量节点 | 默认浏览 | 标题、分类图标、端口 label、1 行摘要 |
| LOD 2 | 激活节点 | 选中、悬停、展开 | 允许 quick controls 或更多摘要 |
| LOD 3 | 编辑节点 | 正在编辑配置 | 挂载 `NodeConfigEditor` 或节点内重型组件 |

建议默认规则：

| 条件 | LOD |
| --- | --- |
| `nodes.length >= 200` 且未选中 | LOD 0 |
| `nodes.length >= 80` 且未选中 | LOD 1 |
| `zoom < 0.45` | LOD 0 |
| `zoom < 0.7` | LOD 1 |
| 当前选中节点 | LOD 2 |
| 当前进入编辑态节点 | LOD 3 |

### 5.7.2 激活态定义

节点是否激活不应依赖复杂组件内部状态，建议由画布统一维护：

```ts
const hoveredNodeId = ref<string | null>(null)
const editingNodeId = ref<string | null>(null)

const activeNodeIds = computed(() => {
  const ids = new Set<string>()
  if (store.selectedNodeId) ids.add(store.selectedNodeId)
  if (hoveredNodeId.value) ids.add(hoveredNodeId.value)
  if (editingNodeId.value) ids.add(editingNodeId.value)
  return ids
})
```

LOD 计算：

```ts
function getNodeLod(nodeId: string, zoom: number, nodeCount: number): 0 | 1 | 2 | 3 {
  if (editingNodeId.value === nodeId) return 3
  if (activeNodeIds.value.has(nodeId)) return 2
  if (nodeCount >= 200 || zoom < 0.45) return 0
  if (nodeCount >= 80 || zoom < 0.7) return 1
  return 1
}
```

### 5.7.3 组件结构

推荐拆成三层：

```text
RuleNode.vue
  ├─ RuleNodeShell.vue        // LOD 0/1，极简/轻量 DOM
  ├─ RuleNodeActive.vue       // LOD 2，激活态轻交互
  └─ NodeConfigEditor.vue     // LOD 3，完整配置编辑
```

`RuleNode.vue` 只做分发：

```vue
<template>
  <RuleNodeActive
    v-if="lod >= 2"
    :data="data"
    :lod="lod"
  />
  <RuleNodeShell
    v-else
    :data="data"
    :lod="lod"
  />
</template>
```

如果完整编辑仍然放右侧属性面板，则 LOD 3 不在节点内挂载 `NodeConfigEditor`，而是：

```text
节点进入 LOD 2
右侧属性面板进入 LOD 3
```

这样更稳，因为画布节点始终保持轻量。

### 5.7.4 图片化策略

图片化可行，但不建议第一阶段直接做。

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 轻量 DOM LOD | 实现简单，端口和选中状态容易保留 | 极限性能不如 Canvas/图片 |
| 图片快照 LOD | 绘制成本最低，适合 500+ 节点 | 缓存失效、缩放清晰度、主题变化、端口定位复杂 |
| Canvas/WebGL 节点层 | 上限最高 | 基本等于重写画布节点渲染 |

推荐路线：

```text
第一阶段：LOD 0/1 用轻量 DOM
第二阶段：如果 300-500 节点仍卡，将 LOD 0 改为图片或 Canvas 快照
第三阶段：只对选中/编辑节点挂载真实 DOM 组件
```

图片快照缓存键建议包含：

```ts
type NodeSnapshotCacheKey = [
  nodeId: string,
  nodeType: string,
  status: string,
  summaryHash: string,
  themeVersion: string,
  lod: number
].join(':')
```

缓存失效条件：

| 条件 | 是否失效 |
| --- | --- |
| 节点标题变化 | 是 |
| 节点状态变化 | 是 |
| 摘要字段变化 | 是 |
| 主题变化 | 是 |
| zoom 变化 | 否，使用高分辨率快照或 SVG |
| position 变化 | 否 |

### 5.7.5 关键约束

LOD 方案要有效，必须满足这些约束：

| 约束 | 原因 |
| --- | --- |
| 重型组件必须用 `v-if` 卸载 | `v-show` 只是隐藏，组件仍然参与响应式 |
| 非激活节点不能扫描全图 | 否则 DOM 简化后 computed 仍然卡 |
| 摘要尽量预计算或缓存 | 避免每个节点每次扫描 schema |
| 连接状态必须使用索引 | 避免 `RuleNode` 扫描 `store.edges` |
| 大图模式关闭动画和阴影 | 防止 paint 成为主瓶颈 |
| LOD 切换需要防抖 | 快速缩放时避免节点反复 mount/unmount |

LOD 切换防抖建议：

```ts
const effectiveZoom = shallowRef(1)
const updateEffectiveZoom = throttle((zoom: number) => {
  effectiveZoom.value = zoom
}, 120)
```

### 5.7.6 与现有方案的关系

LOD 不是替代前面 Phase B/C，而是建立在这些基础上：

| 前置能力 | 是否必须 | 原因 |
| --- | --- | --- |
| 轻量节点壳 | 必须 | LOD 0/1 的基础 |
| 连接状态索引 | 必须 | 非激活节点不能扫描边 |
| 大图模式 | 必须 | 负责控制 LOD 阈值和视觉降级 |
| 命令化历史 | 建议 | 解决拖拽松手冻结 |
| 属性面板 | 建议 | LOD 3 更适合放在画布外 |

| 步骤 | 内容 | 风险 |

## 7.1 最新代码落地方案

基于 2026-06-07 最新代码复盘，Phase A 已基本完成：`NodeConfigEditor.vue` 已拆出，`RuleNode.vue` 已变成轻量节点壳。但当前卡顿仍来自全图边扫描、隐藏控件计算、历史快照、批量操作和 SVG/CSS 绘制。

下面是可直接实施的具体方案，按顺序执行。

### 任务 1: 连接状态索引化

**目标**: 去掉每个 `RuleNode` 扫描 `store.edges` 的 `O(V * E)` 成本。

当前问题位置：

| 文件 | 问题 |
| --- | --- |
| `webui/src/components/rule-engine/RuleNode.vue` | 每个节点内部 computed 扫描 `store.edges` |
| `webui/src/stores/ruleEngine.ts` | 没有全局 connected handle 索引 |

Store 新增索引：

```ts
const connectedHandleIndex = computed(() => {
  const index = new Set<string>()
  for (const edge of edges.value) {
    if (edge.sourceHandle) {
      index.add(`${edge.source}:${edge.sourceHandle}:source`)
    }
    if (edge.targetHandle) {
      index.add(`${edge.target}:${edge.targetHandle}:target`)
    }
  }
  return index
})

function isHandleConnected(
  nodeId: string,
  handleId: string,
  direction: 'source' | 'target'
) {
  return connectedHandleIndex.value.has(`${nodeId}:${handleId}:${direction}`)
}
```

`RuleNode.vue` 改造：

```ts
function isInputConnected(handleId: string): boolean {
  return store.isHandleConnected(props.data.id, handleId, 'target')
}

function isOutputConnected(handleId: string): boolean {
  return store.isHandleConnected(props.data.id, handleId, 'source')
}
```

模板同步改：

```vue
<Handle
  type="target"
  :class="{ 'is-connected': isInputConnected(input.name) }"
/>

<Handle
  type="source"
  :class="{ 'is-connected': isOutputConnected(output.name) }"
/>
```

验收：

| 场景 | 标准 |
| --- | --- |
| 200 节点 / 300 边 | 拖拽时 RuleNode 不再重复扫描边集合 |
| 新增连线 | 两端 handle 连接状态立即更新 |
| 删除连线 | 两端 handle 连接状态立即恢复 |

### 任务 2: 移除隐藏 quick controls 的计算成本

**目标**: quick controls 当前不渲染时，也不再计算 schema 排序和 hash。

当前问题：

| 文件 | 问题 |
| --- | --- |
| `RuleNode.vue` | 模板 `v-if="false"`，但 `quickControlsHash` 仍被根 `v-memo` 使用 |
| `RuleNode.vue` | `quickControlsHash` 会触发 schema 扫描、排序和 `JSON.stringify` |

改造方案：

1. 新增常量：

```ts

```

2. 根 `v-memo` 删除 `quickControlsHash`：

```vue

```

3. `quickControls` 在禁用时直接返回空数组：

```ts
const quickControls = computed(() => {
  if (!ENABLE_QUICK_CONTROLS) return []
  // 原逻辑
})
```

4. `quickControlsHash` 删除，或只在启用 quick controls 时计算。

5. 模板改成真实开关：

```vue
<div
  v-if="ENABLE_QUICK_CONTROLS && quickControls.length > 0"

```

验收：

| 场景 | 标准 |
| --- | --- |
| quick controls 禁用 | 每个节点不再执行 quick schema 排序和 hash |
| 100 节点加载 | RuleNode 初始化成本降低 |
| 后续启用 quick controls | 可以通过常量或 store 开关恢复 |

### 任务 3: 拖拽历史从整图快照改为 move command

**目标**: 拖拽松手不再克隆几百个节点。

当前问题路径：

```text
handleNodeDragStart()
  -> store.pauseHistory()

handleNodeDragStop()
  -> store.unpauseHistory()
  -> saveHistory()
  -> cloneForHistory(nodes.value)
```

几百节点时，拖拽结束会卡顿，因为 `saveHistory()` 克隆整图。

短期可落地方案：先只改拖拽历史，其他操作暂时保留快照历史。

新增拖拽位置缓存：

```ts
const dragStartPositions = new Map<string, { x: number; y: number }>()
```

`handleNodeDragStart` 记录初始位置：

```ts
function handleNodeDragStart({ node }: { node: Node<RuleNodeData> }) {
  isNodeDragging.value = true
  dragStartPositions.set(node.id, { ...node.position })
}
```

`handleNodeDragStop` 只记录 move：

```ts
function handleNodeDragStop({ node }: { node: Node<RuleNodeData> }) {
  isNodeDragging.value = false
  const from = dragStartPositions.get(node.id)
  dragStartPositions.delete(node.id)
  if (!from) return
  store.recordMoveHistory(node.id, from, { ...node.position })
}
```

Store 新增轻量历史类型：

```ts
type MoveHistoryEntry = {
  type: 'node:move'
  nodeId: string
  from: { x: number; y: number }
  to: { x: number; y: number }
}
```

第一阶段可以采用混合历史：

```ts
const historyStack = ref<Array<
  | { type: 'snapshot'; nodes: GraphNode[]; edges: GraphEdge[] }
  | MoveHistoryEntry
>>([])
```

`undo()` 遇到 `node:move` 时只改该节点位置：

```ts
function applyNodePosition(nodeId: string, position: { x: number; y: number }) {
  const node = nodes.value.find(n => n.id === nodeId)
  if (!node) return
  node.position = { ...position }
  triggerRef(nodes)
}
```

验收：

| 场景 | 标准 |
| --- | --- |
| 200 节点单节点拖拽 | 松手不出现明显冻结 |
| 撤销拖拽 | 节点回到拖拽前位置 |
| 重做拖拽 | 节点回到拖拽后位置 |

### 任务 4: 批量删除改为一次性操作

**目标**: 删除多个节点时只 filter 一次、保存一次历史。

当前问题：

```ts
for (const id of nodeIds) {
  store.removeNode(id)
}
```

`removeNode()` 每次都会：

```text
filter nodes
filter edges
saveHistory
```

删除 50 个节点就是 50 次全图操作。

Store 新增：

```ts
function removeNodes(nodeIds: string[]) {
  if (nodeIds.length === 0) return
  const idSet = new Set(nodeIds)
  nodes.value = nodes.value.filter(n => !idSet.has(n.id))
  edges.value = edges.value.filter(e => !idSet.has(e.source) && !idSet.has(e.target))
  if (selectedNodeId.value && idSet.has(selectedNodeId.value)) {
    selectedNodeId.value = null
  }
  saveHistory()
}
```

`RuleCanvas.vue` 改：

```ts
function handleDelete() {
  const vfNodes = getNodes.value as any[]
  const selectedNodes = vfNodes.filter((n) => n.selected)
  const selectedEdges = edges.value.filter((e: any) => e.selected)

  const nodeIds = selectedNodes.map((n) => n.id)
  const edgeIds = new Set(selectedEdges.map(e => e.id))

  if (nodeIds.length > 0) {
    store.removeNodes(nodeIds)
  }
  if (edgeIds.size > 0) {
    store.removeEdges([...edgeIds])
  }
}
```

Store 同步新增 `removeEdges(edgeIds: string[])`。

验收：

| 场景 | 标准 |
| --- | --- |
| 删除 50 节点 | 只触发一次 nodes/edges 赋值 |
| 删除 50 节点 | 只生成一次历史记录 |
| 删除后属性面板 | 不显示已删除节点 |

## 9. 是否需要替换 VueFlow

暂不建议立即替换。

理由：

| 继续 VueFlow | 说明 |
| --- | --- |
| 现有功能完整 | 拖拽、连接、选择、视口、Handle 已集成 |
| 当前瓶颈主要是节点组件过重 | 换库不能自动解决 Element Plus 节点内表单问题 |
| 迁移成本高 | 连接验证、右键、复制粘贴、执行状态都要重做 |

何时考虑替换：

| 条件 | 说明 |
| --- | --- |
| 轻量节点壳后 200 节点仍不可用 | 才说明 VueFlow 本身成为瓶颈 |
| 需要 1000+ 节点长期浏览 | 可考虑 Canvas/WebGL 或 X6/Leafer 方案 |
| 需要复杂 group/subgraph 原生支持 | 可重新评估 AntV X6 |

## 10. 最终建议

大规模规则图的关键不是继续给当前重型节点加 `v-memo`，而是改变编辑模型：

```text
画布负责结构和连线
属性面板负责配置编辑
Store 负责索引和增量状态
大图模式负责降级视觉成本
搜索/分组负责可维护性
```

按这个方向改造后，规则引擎前端才有现实机会支撑几百个节点。
