# 规则引擎大规模节点画布架构方案

**日期**: 2026-06-07
**范围**: WebUI 规则引擎画布 (`RuleCanvas.vue` / `RuleNode.vue` / `ruleEngine.ts`)
**目标**: 支持 200-500 个规则节点的可浏览、可编辑、可保存体验

---

## 1. 背景与结论

当前 WebUI 规则引擎画布已经完成一轮拖拽性能优化，包括：

| 已完成优化 | 作用 |
| --- | --- |
| VueFlow manual control | 避免拖拽中 `v-model:nodes` 每帧回写整图 |
| `nodes` / `edges` 使用 `shallowRef` | 降低 Vue 深响应式代理成本 |
| 拖拽中跳过 position 写回 | 避免 60Hz store 更新 |
| `only-render-visible-elements` | 只渲染视口内节点 |
| RuleNode 根与字段级 `v-memo` | 降低重复渲染 |
| MiniMap 拖拽期间暂停渲染 | 避免缩略图全量节点更新 |

这些优化能改善 30-80 节点的交互，但不足以让几百个复杂规则节点长期流畅。原因不是单个 bug，而是当前设计把“节点配置表单”直接放在画布节点内部，导致每个节点都是重型 Vue + Element Plus 组件。

**核心结论**:

当前设计适合中小规模规则图，不适合几百个完整可编辑节点同时在画布中渲染。要支持 200-500 节点，需要从“重型节点编辑器”改为“轻量节点壳 + 侧边属性面板 + 大图性能模式 + 增量状态管理”。

---

## 2. 目标与非目标

### 2.1 目标

| 目标 | 指标 |
| --- | --- |
| 100 节点正常编辑 | 单节点拖拽接近 60fps，明显无卡顿 |
| 200 节点可用 | 拖拽、缩放、平移、框选不卡死 |
| 500 节点可浏览 | 能打开、定位、搜索、分组查看，不要求所有节点同时精细编辑 |
| 配置编辑稳定 | 节点配置修改只影响当前节点，不触发全图组件更新 |
| 历史记录可控 | 撤销/重做不再每次深克隆整图 |

### 2.2 非目标

| 非目标 | 说明 |
| --- | --- |
| 不追求 500 个复杂表单节点同时可见 | 浏览器 DOM 和 Element Plus 组件成本不现实 |
| 不立即替换 VueFlow | 先利用 VueFlow 现有能力，避免大规模迁移风险 |
| 不做后端执行引擎改造 | 本方案只处理 WebUI 编辑体验 |
| 不一次性完成所有阶段 | 先解决节点渲染和响应式热路径 |

## 3. 当前瓶颈

### 3.1 节点组件过重

当前 `RuleNode.vue` 同时承担四类职责：

| 职责 | 当前实现 | 问题 |
| --- | --- | --- |
| 节点视觉 | 标题、类型、状态、端口 | 合理 |
| 配置编辑 | `el-input` / `el-select` / `el-slider` / `el-checkbox` 等 | 组件数量随节点数线性增长 |
| 变量绑定 | 变量按钮、菜单、输入框 ref | 每个节点维护独立交互状态 |
| 连接状态 | 每个节点扫描 `store.edges` | 边多时重复计算 |

几百节点时，即使视口虚拟化只渲染部分节点，只要视口内有几十个节点，Element Plus 控件、tooltip、select、textarea、slider 仍会带来明显渲染压力。

### 3.2 画布节点和配置编辑耦合

节点配置写入路径目前是：

```text
RuleNode widget
  -> store.updateNodeConfig()
  -> triggerRef(nodes)
  -> RuleCanvas / VueFlow / 可见 RuleNode 响应
```

即使已经用 `v-memo` 降低了重复渲染，配置字段仍然在画布节点内部，无法从根本上降低节点复杂度。

### 3.3 连接状态重复扫描

当前每个 `RuleNode` 内部都有类似逻辑：

```text
connectedHandleIds = computed(() => scan(store.edges))
```

当可见节点数为 V、边数为 E 时，连接状态计算近似为 `O(V * E)`。几百节点通常意味着几百条边，这条路径会成为持续性成本。

### 3.4 历史记录和复制粘贴是整图模型

当前历史记录通过快照保存节点和边：

```text
historyStack.push({
  nodes: cloneForHistory(nodes),
  edges: cloneForHistory(edges)
})
```

这对几十节点可接受，但几百节点时，每次创建、删除、连接、粘贴都会产生较大 JSON clone 和 GC 压力。

### 3.5 大图缺少导航型能力

几百节点规则图不能只依赖缩放和平移。需要搜索、分组、折叠、局部聚焦、子图入口，否则即使性能足够，用户也难以维护。

## 4. 推荐架构

### 4.1 总体结构

```text
┌─────────────────────────────────────────────────────────────┐
│ RuleCanvas.vue                                               │
│                                                             │
│  ┌───────────────────────┐    ┌──────────────────────────┐  │
│  │ VueFlow Canvas         │    │ PropertiesPanel          │  │
│  │                       │    │                          │  │
│  │ LightweightRuleNode   │ -> │ NodeConfigEditor         │  │
│  │ only visual shell     │    │ Element Plus widgets     │  │
│  │ no config widgets     │    │ only selected node       │  │
│  └───────────────────────┘    └──────────────────────────┘  │
│                                                             │
│  ┌────────────────────────────────────────────────────────┐ │
│  │ LargeGraphMode                                         │ │
│  │ minimap off / shadows reduced / edge labels hidden     │ │
│  └────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ Pinia ruleEngine store                                      │
│                                                             │
│ nodes / edges                                                │
│ selectedNodeId                                               │
│ connectedHandleIndex: Set<string>                            │
│ history: command log + periodic snapshots                    │
└─────────────────────────────────────────────────────────────┘
```

核心变化：

| 改造点 | 改造前 | 改造后 |
| --- | --- | --- |
| 节点组件 | 节点内直接编辑配置 | 节点只显示轻量视觉壳 |
| 配置编辑 | 每个节点都有 Element Plus 控件 | 只有右侧属性面板渲染当前选中节点控件 |
| 连接状态 | 每个节点扫描全部边 | Store 维护全局连接索引，节点 O(1) 查询 |
| 大图策略 | 所有图同一渲染模式 | 超过阈值自动进入性能模式 |
| 历史记录 | 每步整图快照 | 操作日志 + 周期快照 |

## 5. 详细设计

### 5.1 轻量节点壳

新增或改造 `RuleNode.vue` 为轻量节点壳，只保留：

| 保留内容 | 说明 |
| --- | --- |
| 节点标题 | `data.label` / `data.type` |
| 分类图标 | 输入、检测、处理、动作、逻辑、输出 |
| 执行状态 | idle / running / success / failed / timeout |
| 输入输出端口 | Handle + 简短 label |
| 配置摘要 | 最多 1-2 行关键字段摘要，可选 |

移除或迁移：

| 移出节点内容 | 迁移位置 |
| --- | --- |
| `el-input` / `el-select` / `el-slider` / `el-checkbox` | 右侧 `NodeConfigEditor.vue` |
| 变量绑定按钮和菜单 | 右侧属性面板 |
| 文件选择器 | 右侧属性面板 |
| 模型选择器 | 右侧属性面板 |
| 输入框 ref / 光标插入逻辑 | 右侧属性面板 |

建议节点模板结构：

```vue
<template>
  <div class="rule-node-shell" :data-status="data.status">
    <header class="node-header">
      <SvgIcon :name="categoryIcon" />
      <span class="node-title">{{ data.label }}</span>
    </header>

    <section class="node-summary" v-if="summary">
      {{ summary }}
    </section>

    <section class="node-ports">
      <!-- input/output handles -->
    </section>
  </div>
</template>
```

预期收益：

| 指标 | 当前 | 改造后 |
| --- | --- | --- |
| 每节点 Element Plus 控件 | 0-6 个 | 0 个 |
| 每节点交互状态 | 多个 ref / computed | 少量 computed |
| 可见 30 节点 DOM 压力 | 高 | 中低 |

### 5.2 右侧属性面板

新增 `NodeConfigEditor.vue`，接管所有配置控件。

输入：

```ts
interface NodeConfigEditorProps {
  nodeId: string
  data: RuleNodeData
}
```

职责：

| 职责 | 说明 |
| --- | --- |
| 根据 `configSchema` 渲染控件 | 保留现有 widget 能力 |
| 调用 `store.updateNodeConfig()` | 保持单源 store |
| 处理变量绑定 | 光标插入、变量菜单、格式校验 |
| 处理模型选择 | `availableModels` / 类别加载 |
| 处理文件选择 | file-picker |

`RuleCanvas.vue` 右侧属性区域只渲染当前选中节点：

```vue
<NodeConfigEditor
  v-if="selectedNode"
  :node-id="selectedNode.id"
  :data="selectedNode.data"
/>
```

这样几百节点时，配置控件数量始终约等于“一个节点”的控件数量。

### 5.3 连接状态索引

在 `ruleEngine.ts` 中新增连接索引：

```ts
const connectedHandleIndex = computed(() => {
  const index = new Set<string>()
  for (const edge of edges.value) {
    if (edge.sourceHandle) {
      index.add(`${edge.source}:${edge.sourceHandle}:source`)
    }
    if (edge.targetHandle) {
      index.add(`${edge.target}:${edge.targetHandle}:target`)
    }
  }
  return index
})
```

节点内查询改为：

```ts
function isHandleConnected(nodeId: string, handleId: string, direction: 'source' | 'target') {
  return store.connectedHandleIndex.has(`${nodeId}:${handleId}:${direction}`)
}
```

收益：

| 当前 | 改造后 |
| --- | --- |
| 每个可见节点扫描全部边 | Store 对边集合统一计算一次 |
| `O(V * E)` | `O(E + V * H)` |

其中 V 是可见节点数，E 是边数，H 是每个节点 handle 数。

### 5.4 大图性能模式

新增 `largeGraphMode`：

```ts
const LARGE_GRAPH_NODE_THRESHOLD = 80
const HUGE_GRAPH_NODE_THRESHOLD = 200

const largeGraphMode = computed(() => nodes.value.length >= LARGE_GRAPH_NODE_THRESHOLD)
const hugeGraphMode = computed(() => nodes.value.length >= HUGE_GRAPH_NODE_THRESHOLD)
```

大图模式策略：

| 策略 | 触发 |
| --- | --- |
| MiniMap 默认关闭 | `nodes.length >= 80` |
| 拖拽中关闭 MiniMap | 所有规模 |
| 隐藏边 label / 动画 | `nodes.length >= 80` |
| 降低节点阴影和状态 glow | `nodes.length >= 80` |
| 节点摘要折叠 | `nodes.length >= 200` |
| 提示用户使用搜索/分组 | `nodes.length >= 200` |

注意：大图模式不应该破坏用户显式设置。建议区分“系统自动关闭”和“用户手动打开”：

```ts
const minimapPreference = ref<'auto' | 'on' | 'off'>('auto')
const shouldShowMiniMap = computed(() => {
  if (isNodeDragging.value || isSelectionDragging.value) return false
  if (minimapPreference.value === 'on') return true
  if (minimapPreference.value === 'off') return false
  return !largeGraphMode.value
})
```

### 5.5 历史记录改造

当前历史记录是整图快照，建议改成操作日志为主、周期快照为辅。

操作类型：

```ts
type GraphCommand =
  | { type: 'node:create'; node: Node }
  | { type: 'node:delete'; node: Node; relatedEdges: Edge[] }
  | { type: 'node:move'; nodeId: string; from: XYPosition; to: XYPosition }
  | { type: 'node:update-config'; nodeId: string; key: string; from: unknown; to: unknown }
  | { type: 'edge:create'; edge: Edge }
  | { type: 'edge:delete'; edge: Edge }
  | { type: 'batch'; commands: GraphCommand[] }
```

历史结构：

```ts
interface HistoryState {
  checkpoints: Array<{ index: number; nodes: Node[]; edges: Edge[] }>
  commands: GraphCommand[]
  cursor: number
}
```

策略：

| 策略 | 说明 |
| --- | --- |
| 普通操作记录 command | 避免整图克隆 |
| 每 20-30 步保存 checkpoint | 避免 undo 很多步时重放过长 |
| 拖拽只记录 start/end | 不记录中间帧 |
| 批量粘贴/删除记录 batch | 保证撤销语义完整 |

阶段 1 可先保留快照历史；阶段 3 再改命令历史。

### 5.6 大图导航能力

几百节点需要导航辅助，否则性能达标也难维护。

推荐新增能力：

| 能力 | 说明 |
| --- | --- |
| 节点搜索 | 按名称、类型、分类、配置关键字搜索 |
| 定位节点 | 搜索结果点击后 `setCenter()` |
| 分类筛选 | 只突出或只显示某类节点 |
| 折叠分组 | 将局部链路折叠成 group/subgraph |
| 依赖邻域查看 | 只突出当前节点上下游 N 层 |

优先级最高的是搜索定位和上下游突出，投入小、收益高。

## 6. 分阶段实施计划

### Phase A: 轻量节点壳

**目标**: 去掉画布节点内的配置表单。

改动：

| 文件 | 动作 |
| --- | --- |
| `RuleNode.vue` | 保留标题、状态、端口、摘要，移除配置控件 |
| `NodeConfigEditor.vue` | 新增配置编辑组件，迁移 widget 渲染逻辑 |
| `RuleCanvas.vue` | 右侧属性面板渲染 `NodeConfigEditor` |

验收：

| 场景 | 标准 |
| --- | --- |
| 100 节点 | 单节点拖拽明显流畅 |
| 配置编辑 | 所有原有 widget 可编辑 |
| 变量绑定 | 光标插入和变量菜单可用 |
| 模型选择 | 模型下拉和类别刷新可用 |

风险：

| 风险 | 缓解 |
| --- | --- |
| 迁移配置控件时漏掉 widget | 以现有 `RuleNode.vue` widget 分支逐项迁移 |
| 用户习惯节点内编辑 | 属性面板是大图编辑器更稳定的交互模式 |

### Phase B: 连接索引与大图模式

**目标**: 降低边状态计算和大图视觉成本。

改动：

| 文件 | 动作 |
| --- | --- |
| `ruleEngine.ts` | 新增 `connectedHandleIndex` |
| `RuleNode.vue` | 使用 O(1) handle 连接查询 |
| `RuleCanvas.vue` | 新增 `largeGraphMode` / `shouldShowMiniMap` |
| 样式文件 | 大图模式下降低阴影、动画、边 label |

验收：

| 场景 | 标准 |
| --- | --- |
| 200 节点 / 300 边 | 拖拽不出现秒级卡顿 |
| 连线新增删除 | handle 高亮状态正确 |
| 用户手动打开 MiniMap | 可打开，但拖拽期间仍暂停 |

### Phase C: 历史记录命令化

**目标**: 降低撤销/重做和批量操作的整图 clone 成本。

改动：

| 文件 | 动作 |
| --- | --- |
| `ruleEngine.ts` | 引入 `GraphCommand` |
| 节点/边操作方法 | 记录 command 而不是每次快照 |
| undo/redo | 按 command 反向/正向应用 |

验收：

| 场景 | 标准 |
| --- | --- |
| 200 节点连续拖拽 20 次 | 历史记录内存增长可控 |
| 批量粘贴 50 节点 | 可一次撤销 |
| 删除带边节点 | 撤销后节点和边完整恢复 |

### Phase D: 大图导航与子图

**目标**: 让几百节点可维护。

改动：

| 功能 | 动作 |
| --- | --- |
| 搜索定位 | 节点名称/类型/配置搜索 |
| 上下游突出 | 当前节点 N 层邻域高亮 |
| 分组折叠 | 支持将节点集合折叠为 group |
| 子图入口 | 双击 group 进入局部编辑 |

验收：

| 场景 | 标准 |
| --- | --- |
| 500 节点 | 能快速搜索并定位目标节点 |
| 复杂链路 | 能突出上下游依赖 |
| 分组规则 | 折叠后画布可读性提升 |

## 7. 推荐优先级

| 优先级 | 工作 | 原因 |
| --- | --- | --- |
| P0 | Phase A 轻量节点壳 | 几百节点可用的前提 |
| P0 | Phase B 连接索引 | 消除边状态重复扫描 |
| P1 | Phase B 大图模式 | 降低视觉和辅助组件成本 |
| P1 | 搜索定位 | 大图维护必需 |
| P2 | Phase C 命令历史 | 大量编辑后降低内存和 GC |
| P2 | 分组/子图 | 复杂规则图长期治理 |

最建议先做：

```text
1. RuleNode 轻量化
2. NodeConfigEditor 迁移配置控件
3. connectedHandleIndex
4. largeGraphMode
```

这四项完成后，再评估是否需要替换画布库或做子图架构。

## 9. 是否需要替换 VueFlow

暂不建议立即替换。

理由：

| 继续 VueFlow | 说明 |
| --- | --- |
| 现有功能完整 | 拖拽、连接、选择、视口、Handle 已集成 |
| 当前瓶颈主要是节点组件过重 | 换库不能自动解决 Element Plus 节点内表单问题 |
| 迁移成本高 | 连接验证、右键、复制粘贴、执行状态都要重做 |

何时考虑替换：

| 条件 | 说明 |
| --- | --- |
| 轻量节点壳后 200 节点仍不可用 | 才说明 VueFlow 本身成为瓶颈 |
| 需要 1000+ 节点长期浏览 | 可考虑 Canvas/WebGL 或 X6/Leafer 方案 |
| 需要复杂 group/subgraph 原生支持 | 可重新评估 AntV X6 |

## 10. 最终建议

大规模规则图的关键不是继续给当前重型节点加 `v-memo`，而是改变编辑模型：

```text
画布负责结构和连线
属性面板负责配置编辑
Store 负责索引和增量状态
大图模式负责降级视觉成本
搜索/分组负责可维护性
```

按这个方向改造后，规则引擎前端才有现实机会支撑几百个节点。
