## Phase 10: 端到端可用性 — P0 阻断项

### 10.1 model-select widget 对接模型管理 API ✅ 已完成
**问题：** yolo_model / yolo_trigger 节点的 configSchema 中定义了 `widget: "model-select"`，但前端渲染时仅显示空下拉，未从后端获取模型列表。用户无法选择模型。

**解决方案：** 前端架构重构为 Pinia Store 单源模式， Store 新增 `availableModels` + `fetchModels()`， `onMounted` 独立 try-catch 确保模型列表加载不受前置 API 失败影响。RuleNode 通过 `computed(() => store.availableModels)` 读取，空列表时显示提示。

**涉及文件：**
- `webui/src/stores/ruleEngine.ts` — 新增 `availableModels` 状态和 `fetchModels()` 方法
- `webui/src/components/rule-engine/RuleNode.vue` — model-select widget 渲染逻辑，从 Store 读取模型列表
- `webui/src/views/RuleCanvas.vue` — `onMounted` 独立 try-catch 调用 `fetchModels()`
- `webui/src/api/` — 使用已有的 `modelApi.list()`

✅ **验收通过**：yolo_model 节点配置下拉展示已训练模型列表，空列表时显示"暂无可用模型"。

### 10.2 执行超时保护 ✅ 已完成
**问题：** 当前节点执行没有超时机制。如果某个节点（如 http_request_action 请求外部服务、yolo_model 加载大模型）卡住，整个执行引擎会无限等待。

**解决方案：**
- 全局默认超时：300s（5 分钟），可在执行上下文中覆盖
- BaseExecutor 可选 `default_timeout` 类属性，子类（如 yolo_model）可覆盖
- 专用 `node_timeout` WebSocket 事件（区别于通用 `node_failed`，前端用 warning 级别展示）
- 超时后标记节点为 `timeout`，继续执行下游（断路器模式）
- 12 个单元测试覆盖默认/上下文/显式/子类/事件/端到端六类场景

**涉及文件：**
- `backend/services/rule_engine/executor.py` — `_execute_node()` 使用 `asyncio.wait_for()`
- `backend/services/rule_engine/nodes/base.py` — BaseExecutor `default_timeout` 字段
- `backend/websocket_manager.py` — `send_node_timeout()` 新增
- `webui/src/views/RuleCanvas.vue` — `case 'node_timeout'` 处理
- `backend/tests/test_rule_engine/test_execution_timeout.py` — 12 个测试

✅ **验收通过**：模拟 sleep 超过 default_timeout 的节点，确认执行引擎在超时后继续执行下游节点；前端 warning 级别提示。

### 10.3 Phase 10 Bug 修复 ✅ 已完成（2026-06-02 提交 `aaafd93`）
Pinia Store 单源模式落地后端到端启动异常，3 个 Bug 修复：
- WebSocket 关闭前未建立警告（增加 `intentionalDisconnect` 标志 + setTimeout 句柄保存/清理）
- back-btn renderSlot null 'ce' 崩溃（`el-button` 改回原生 `<button>`，规避快速卸载时 vnode.ce 为 null 的边缘 case）
- variables provide/inject 双源清理（删除 RuleCanvas 错误 provide， RuleNode 改用 `computed(() => store.variables)`）

## Phase 12: 体验优化 — P2

### 12.1 screen_capture region 序列化 ✅ 已完成
**问题：** `screen_capture.region` 输出端口类型为 OBJECT，但未定义序列化格式，下游节点无法解析。

**解决方案：** 在 `models.py` 中定义 `Region` Pydantic model（字段：x, y, width, height 必填 + monitor 可选），ScreenCaptureNode 兼容 dict / Region 实例 / 非法 dict（透传容错），16 个单元测试。

✅ **验收通过**：Region 可被下游节点 `model_validate()` 安全解析；非法输入不阻塞主流程。

### 12.2 新节点类型 — template（文本/JSON 模板渲染） ✅ 已完成
**问题：** 用户需要根据上游数据生成 webhook payload / SQL 语句 / 日志消息等结构化输出，无现成节点。

**解决方案：** `template` 节点（PROCESSING），输入 data（OBJECT, 可选），输出 result + raw；配置 template（textarea, `{{var}}` 与 `{{nested.key}}` 插值）+ parse_as（dropdown: text/json）。变量优先级 `trigger_data < context.variables < inputs.data`。31 个单元测试。

✅ **验收通过**：模板可生成文本或解析为 JSON（失败回退为字符串），未定义变量渲染为空。

### 12.3 节点面板按端口类型过滤 ✅ 已完成
**问题：** 节点面板搜索仅按 label/type/description 过滤，找节点时不知道哪些节点有 IMAGE 输入 / STRING 输出。

**解决方案：** 搜索框下方新增端口类型按钮组（全部 / 图像 / 检测框 / 模型 / 字符串 / 控制），激活态青色高亮。任一输入或输出端口匹配即通过，与文本搜索 AND 组合。

✅ **验收通过**：用户可按"我要接收 IMAGE 的节点"快速过滤。

## Phase 13: 端到端验收 + 节点扩展 ✅ 已完成

### 13.1 新增 merge_detections 节点（多 YOLO 模型融合） ✅ 已完成
**动机：** v2 计划原列 12.2.4 候选节点，Phase 13 正式落地。

**实现：** `merge_detections` 节点（PROCESSING），8 路 ARRAY 输入 `input_1` ~ `input_8`，输出 `merged` + `count`；配置 `iou_threshold`（slider, 默认 0.5）+ `strategy`（dropdown: nms/union）+ `keep_source`（checkbox, 默认 False）。NMS 策略按 IoU 去重保留最高置信度，union 简单拼接不去重；keep_source 在每个检测 dict 加 `source` 字段（input_N）便于溯源。25 个单元测试。

### 13.2 新增 roi_extract 节点（按 BBOX 裁剪 ROI） ✅ 已完成
**动机：** v2 计划原列 12.2.5 候选节点，Phase 13 正式落地。

**实现：** `roi_extract` 节点（PROCESSING），输入 `image`（IMAGE）+ `detections`（ARRAY, 含 bbox 字段），输出 `roi`（第一张）+ `roi_count` + `width`/`height`；配置 `padding`（slider, 默认 0.0）/ `min_size`（number, 默认 4）/ `max_rois`（number, 默认 10，按 confidence 降序截取）。11 个单元测试（其中 10 个依赖 cv2， 在 cv2 已装环境 skip）。

### 13.4 端到端 P0/P1 Bug 修复（4 个） ✅ 已完成（2026-06-04 提交 `e14c587c`）
**动机：** Phase 13 节点功能完整，但实际跑推理图仍失败。根因不是新节点代码，而是历史代码中积累的几个执行链路缺陷。

**Bug 1：NodeExecutionLog 表缺列（P0）**
- 现象：执行任何图报 `sqlalchemy.exc.OperationalError: no such column: node_execution_log.duration_ms`
- 根因：Phase 11.1（0f5e7d2）加 `duration_ms` / `metrics_json` 字段到 model 但没写迁移脚本
- 修复：`backend/database.py init_db()` 加 2 行 `_migrate_add_column`（幂等执行，列已存在静默跳过）

**Bug 2：graph validate 不识别 VueFlow 节点格式（P0）**
- 现象：前端保存的图调 `/api/rule-engine/graphs/{id}/validate` 报"规则图没有起始触发器节点"
- 根因：validate 用 `node["type"]` 顶层，但 VueFlow 把节点种类（custom/group）放在顶层 type，节点类型在 `node.data.type`
- 修复：`graph_manager.py` 加 `get_node_type()` 内部函数 + `_VUEFLOW_PLACEHOLDER_TYPES` 白名单（custom/group/default/input/output），同时兼容后端老格式与 VueFlow 格式

**Bug 3：`/api/health` 路由被前端 catch-all 拦截（P0）**
- 现象：GET `/api/health` 返回 index.html（前端 SPA 兜底）
- 根因：`app.py` 中 `app.get("/{path:path}")` catch-all 在 `@app.get("/api/health")` 之前注册， FastAPI 按注册顺序匹配，catch-all 永远优先
- 修复：`app.py` 把 `/api/health` 端点移到 catch-all `serve_frontend` 之前注册，并删除原位置（之前有两份定义）；加注释说明顺序敏感性

**Bug 4：`init_builtin_executors()` 注册到临时实例而非单例（P1）**
- 现象：所有节点执行报"未知的节点类型: manual_trigger"
- 根因：`registry.py:224` 创建 `NodeRegistry()` 新实例注册，但 `executor.py:592` 用 `get_registry()` 拿单例（永远是空）， `app.py` 启动也未调 `init_builtin_executors()`
- 修复：1) registry.py 改用 `get_registry()` 在单例上注册；2) app.py 启动 lifespan 加 `init_builtin_executors()` 强制初始化

**端到端验证**（重启后端 → 创建 VueFlow 格式图 → execute）：
- 修复前：`execution.status=pending` 挂死 / "未知节点类型" failed
- 修复后：`manual_trigger status=completed`, `merge_detections status=completed`
- `node_logs` 完整记录（含 `duration_ms` / `metrics_json`）
- `/api/health` → `{"status":"ok"}`

**回归**：`PYTHONPATH=. pytest backend/tests/test_rule_engine/ -q` → 202 passed, 0 failed, 10 skipped（无回归）。
