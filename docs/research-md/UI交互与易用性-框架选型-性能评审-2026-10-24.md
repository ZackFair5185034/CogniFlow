> 🎯 回应问题：UI 交互设计上有什么问题、易用性要改进什么、框架技术是否可行、性能能否支撑

## 0. 三个结论

| 维度 | 结论 |
|------|------|
| **框架选型** | **不要换框架。** VueFlow 1.48.2 + 应用层自研是对的。fork 的两个能力已被应用层等价覆盖；真正的瓶颈是 `RuleNode.vue` 里的 Element Plus 控件，而这是换 X6/LeaferUI 也解决不了的（项目自己的调研已判定为 deal-breaker）。 |
| **易用性** | **交互规范落地率约 55%。** 「拖节点→连线→配参数→保存→运行→看结果」这条主线在**连线**和**看结果**两处断裂——而且都是静默失败。 |
| **性能支撑** | **80 节点安全，120 起劣化，200 进入保存/编辑卡顿区，500 不可用。** 但虚拟化是真生效的（400 节点只渲染 18 个节点壳），所以瓶颈不在画布框架，在「选中态全图重建」「配置编辑全节点广播」「整图序列化」三处。 |

**但本次实测挖出一条比上面三条都更致命的**：

> ## ⛔ 阻断级发现：BOOLEAN → TRIGGER 的连线被静默丢弃，**动作层事实上不可达**
>
> 实测 400 节点图，控制台 **66 条** `[Vue Flow]: An edge needs a source and a target`，
> 全部指向 `confidence_threshold_condition.result(BOOLEAN) → log_action.trigger(TRIGGER)`。
> 同为 `cond.result` 源、但目标是 `branch.condition(BOOLEAN)` 的边**正常渲染**——差别只在目标端口类型。
>
> 根因在前端 `RuleCanvas.vue:2450-2456` 的 `isPortCompatible`：
>
> ```js
> if (sourceType === 'ANY' || targetType === 'ANY') return true
> if (sourceType === targetType) return true
> if (sourceType === 'TRIGGER' && (targetType === 'TRIGGER' || targetType === 'CONTROL')) return true
> if (sourceType === 'CONTROL' && targetType === 'CONTROL') return true
> return false
> ```
>
> **只有 4 条规则**，而后端 `executor.py:33-51` 的 `PORT_COMPATIBILITY` 有 **14 类源类型**的完整矩阵。
> 前端**禁止 BOOLEAN→TRIGGER**（后端明确允许：`"BOOLEAN": ["ANY","BOOLEAN","TRIGGER","CONTROL"]`）。
>
> 而 **6 个动作/输出节点（键盘、鼠标、HTTP、日志、等待、通知）的输入端口类型全是 `TRIGGER`**，
> 全库**没有任何节点输出 `TRIGGER`**。
>
> **结论：在画布上，「条件 → 动作」这条业务主线连不出来；连出来也不会被渲染。**
> 叠加 `isValidConnection` 返回 `false` 时 VueFlow 直接拦截、不触发 `connect`
> （于是 `handleConnect:2506` 的错误 Toast 永不执行），用户只会看到**「线拖过去没反应，也没有任何提示」**。
>
> 这就是「规则引擎最实用，却根本没跑通业务」的 UI 层根因。

## 1. 框架选型：不要换，但有两处耦合要修

### 1.1 为什么不用换

**fork 的能力已被应用层等价覆盖**（`docs/research-md/vueflow-fork-*.md` → 当前实现）：

| fork 能力 | 应用层等价物 | 评价 |
|-----------|-------------|------|
| skipTrigger（拖拽期 0 响应式写入） | `useCogniFlowDrag.ts:246` 直写 `el.style.transform` | ✅ 等价且更强（O(incident) 而非 O(N×M)） |
| 拖拽期边不重算 | `useEdgePathUpdater.ts:143-196` 增量写 SVG path `d` | ✅ 超出 fork 能力 |
| 框选期跳过 O(N) 包围盒 | `RuleCanvas.vue:1888` 置空 `userSelectionRect` 阻断 Pane `onPointerMove` | ✅ 等价 |
| 框选结束只算一次 | `RuleCanvas.vue:2068` `syncSelectionToStoreNodes` 一次性同步 | ✅ 等价 |
| 框选**过程**实时高亮跟随 | 当前是松手才算（`RuleCanvas.vue:1895`） | ⚠️ 刻意取舍，非回归 |

**换框架解决不了真瓶颈**：真实瓶颈是节点内嵌 Element Plus 表单（`RuleNode.vue:139-150`）。
项目自己的调研已判定：`docs/archives-md/leafer-ui-迁移可行性调研-已选VueFlow.md:372`
「R4 RuleNode.vue Element Plus 控件无法 canvas 化 | 极高 | **致命** | deal-breaker」。

**对标物的真实含义**（这点常被误读）：

- **Node-RED 用 SVG + D3，不是 Canvas**，且无虚拟化、靠 dirty flag，适合 <1000 节点
  （`docs/archives-md/Node-RED编辑器架构研究.md:23`、`:76`、`:188`）
  → **支持"不要 Canvas 化"**
- **ComfyUI 用 Canvas 自绘**，理由是「完全控制性能优化、避免虚拟 DOM 开销」
  （`docs/research-md/节点图数据结构设计.md:327`、`:332-334`）
  → **但 ComfyUI 的节点内控件也是 Canvas 自绘的**。CogniFlow 做不到，因为 `RuleNode.vue` 依赖 Element Plus。
  → **ComfyUI 能用 Canvas 的前提条件，CogniFlow 不具备**，「照抄 ComfyUI」这条路的门槛在节点里，不在画布。

### 1.2 选型结论表

| 方案 | 成本 | 收益 | 何时该选 |
|------|------|------|---------|
| **VueFlow + 应用层自研（现状）** | 0 | 已满足 50–200 节点 | **默认，保留** |
| 维护 VueFlow fork | 高（每版本重跟） | **≈0**（能力已覆盖） | **不推荐**，纯负担 |
| 换 X6 | 1–2 周 | 内置 Scroller 虚拟化 | 节点稳定 > 500 且实测掉帧时。注意 X6 也是 SVG+foreignObject，非 Canvas |
| 换 LeaferUI | 2–4 月 | 理论性能 | **永不**（Element Plus 无法 canvas 化，deal-breaker） |
| 自研 Canvas/WebGL | 6+ 月 | 理论性能 | **永不**（等于重写 RuleNode + 全套图原语） |

### 1.3 不换框架但必须修的两处脆弱耦合

| # | 问题 | 证据 | 后果 |
|---|------|------|------|
| **D2** | 边路径坐标靠读 DOM attribute 反推 `pathEl.getAttribute('sourceX')` | `useEdgePathUpdater.ts:110-113` | 依赖 VueFlow **未文档化的内部行为**（`BaseEdge` 的 `mergeProps` 透传 attrs），升级即可能断 |
| **D3** | 自研 Bezier 公式与官方不等价：官方按 `Position` 分四分支，自研只算 Right→Left 单一方向 | `useEdgePathUpdater.ts:177-182` vs `vue-flow-core.mjs:7308-7336` | 节点左右相对位置变化时，**拖动中边形状与松手后跳变** |

**修法（低风险）**：
- D2 → 改用 `findEdge(id)` 取 `edge.sourceX/sourceY`（VueFlow 已挂在 edge 对象上，`vue-flow-core.mjs:8913-8916`）
- D3 → 改用 `@vue-flow/core` 已导出的 `getBezierPath`，代码从 40 行降到 5 行

### 1.4 另外两处真实缺陷（框架无关）

- **D1 框选命中测试走 DOM**：`RuleCanvas.vue:2035` `container.querySelectorAll('.vue-flow__node[data-id]')`
  + `RuleCanvas.vue:553` `only-render-visible-elements="true"`
  → **视口外的节点没有 DOM，框不到**。用户以为能框远处节点，实际只能框视口内的。
  这是**与节点数无关的纯功能缺陷**，200 节点时就会暴露。
  **修法**：改走 `store.nodes` 的 position + dimensions，在 flow 坐标系做 AABB。

- **D7 内置多选拖拽仍在运行**：VueFlow Pane 无条件 `useDrag` 绑 `.vue-flow__nodesselection-rect`，
  项目仅用 CSS `display:none` 隐藏（`RuleCanvas.vue:4139-4141`）。当前安全，但一旦改 CSS 就会与自研 d3-drag 双写 position。
  属**脆弱耦合**，建议显式 `nodes-selectable=false` 或移除该绑定。

## 3. 性能支撑：瓶颈不在画布框架

### 3.1 实测数据（隔离环境：临时 DATA_DIR + 独立端口 18081 + vite 5173）

| 规模 | 首次加载（vite dev，含模块加载） | 二次加载（模块已缓存） | DOM 中实际渲染的节点 | 渲染节点壳体积 |
|------|------------------------------|--------------------|------------------|--------------|
| 100 节点 | 1814 ms | — | **18 / 100** | ≈7.4 KB/节点 |
| 400 节点 | — | **328–497 ms** | **18 / 400** | `.vue-flow__nodes` 容器 133 KB |

**结论 A：虚拟化是真生效的。**
`only-render-visible-elements="true"`（`RuleCanvas.vue:553`）在 VueFlow 侧对应
`getNodes` computed 调 `getNodesInside`（`vue-flow-core.mjs:7820-7835`），
**DOM 节点数与总节点数解耦**。400 节点和 100 节点渲染量相同（18 个）。
边也虚拟化（100 节点时 9/83 条边进 DOM）。

**结论 B：单节点壳 7.4 KB 太重。** LOD 1 的节点壳仍包含：
`node-header`（图标 SVG + 标题 + 折叠按钮）+ **全部端口的 label + handle** +
**完整的 `node-config-editor` 组件实例**（`nce-preview-mode nce-inline` → `nce-body` → 「该节点无需配置」）。
LOD0 才真正卸载配置区（`RuleNode.vue:140` `v-if="isExpanded && lodLevel >= 1"`）。

**结论 C：加载耗时的绝大部分是 Vite dev 模式**，不是应用。1814 → 328 ms 的差值是模块编译缓存。
真实生产构建下应显著更快，**但未做生产构建下的实测**（见 §5 未验证项）。

### 3.2 真正的瓶颈（代码级）

| 优先级 | 瓶颈 | 复杂度 | 证据 |
|--------|------|--------|------|
| **P0** | **选中态 → VueFlow 全图重建** | 每次选中 O(N)+O(E) | `RuleCanvas.vue:2609-2631` `handleNodesChange` 对 select change 仍 `store.nodes = newNodes`（数组引用替换）→ 触发全量 `createGraphNodes`。文档承诺的「P0-B 改 triggerRef」**未实施** |
| **P0** | **配置编辑 → 全节点广播** | 每次按键 O(N) | `graph.ts:800` `updateNodeConfig` 用 `find`；`graph.ts:806` `_configVersion++` 使**全部 N 个 NodeConfigEditor 重渲染**（`NodeConfigEditor.vue:393-398`） |
| **P1** | **整图序列化（周期 + 同步写）** | O(N+E) 每 5 秒 | `RuleCanvas.vue:2293-2297` dirty 时每 5s `saveDraftToLocalStorage` → `graph.ts:533-548` 全图 stringify + **同步 localStorage 写** |
| **P1** | **O(E²) 索引重建** | undo 路径 | `graph.ts:183` `edges.value.find()` 置于 O(E) 循环内 → E=500 时 25 万次比较 |
| **P1** | **缩略图 O(E×N)** | 每次缩略图 | `RuleCanvas.vue:2877-2886` 每条边两次 `nodes.find`，前置 `vueFlow.toObject()` 本身是全图 `JSON.parse(JSON.stringify())` |
| **P2** | **框选强制回流** | O(V) 次 `getBoundingClientRect` | `RuleCanvas.vue:2035-2050`，06-14 档 §5.1 PERF-1 已提缓存方案，**未实施** |

**做得好、应保留的**（别改坏）：
`only-render-visible` 虚拟化 ✅、d3-drag 事件委托（200 节点 init 60ms→1ms）✅、
拖拽期直写 DOM transform ✅、边增量写 `d` ✅、LOD 短路 + zoom 桶化 ✅、
`connectedHandleIndex` 增量维护 ✅、`nodeById` 依赖追踪断链已修 ✅、
`markRaw` 覆盖创建路径 ✅、事件监听全部配对无泄漏 ✅、历史栈有上限 ✅。

### 3.3 规模上限（定量）

项目自测基线（commit `b81c5b8`）：80 节点加载长任务 3822→711 ms，拖拽 60.5 FPS，框选 120 FPS。

| 规模 | 表现 | 先崩的能力 |
|------|------|-----------|
| **≤80** | ✅ 可用 | 无 |
| **80–120** | 交互流畅，加载 ~1.1s，缩放可感知 | — |
| **120–200** | ⚠️ 明显劣化：单击节点即触发全图重建；改一个配置触发 N 个编辑器重渲染 | 选中态、配置编辑 |
| **200–500** | ⚠️ 保存 / 撤销 / 草稿进入卡顿（undo 深拷 + 每 5s 全图 stringify + O(E²) 索引重建） | 保存、撤销、草稿 |
| **>500** | ❌ 缩略图 O(E×N) + 全图 toObject 深序列化 → 不可用 | 缩略图 |

**先崩的三个点排序**：
1. 选中态全图重建（最高频）
2. 配置编辑全节点广播（最高频连续）
3. 整图序列化（周期性 + 同步 localStorage 写）

## 5. 未验证项 / 已知风险（诚实标注）

1. **未做生产构建下的性能实测**。1814 ms → 328 ms 的差值主要来自 Vite dev 模块编译缓存，**生产 bundle 下的加载/拖拽帧率未测**。§3.1 的「二次加载」是 dev 模式热缓存，不是生产数字。
2. **无帧率/FPS 实测**。项目无 Playwright 配置，浏览器工具也不支持在页面内执行任意 JS，因此「60 fps」「120 FPS」这类数字来自项目自身 commit `b81c5b8` 的 CDP 采样，**本次未独立复现**。本次给出的是「DOM 渲染量」这个更硬的指标。
3. **D3（边形状跳变）与 D5（触控失效）为代码推导结论**，未经浏览器实测。
4. **BOOLEAN→TRIGGER 被丢弃的完整机制未逐行走完 VueFlow 源码**。已确证的是三件事：① 前端 `isPortCompatible` 明确禁止该组合（`RuleCanvas.vue:2450-2456`）；② 后端明确允许（`executor.py:33-51`）；③ 该类边 100% 被 VueFlow 丢弃并有控制台警告，实测 66/66。VueFlow 内部的 handle 解析路径未逐行追完，但**结果与结论不受影响**。
5. **本次造图脚本第一版用了驼峰 `sourceHandle`、第二版用了非法端口配对**，两次都产生了 133 条 EDGE_INVALID 警告。**这是测试床缺陷，已修正为与生产一致的蛇形 + 合法端口配对**，修正后警告降到 66 条且全部指向 BOOLEAN→TRIGGER。**这两批噪声不计入产品缺陷。**
6. **易用性清单基于静态代码分析**，未逐条走完整用户路径。
