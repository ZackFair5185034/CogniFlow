# CogniFlow 规则引擎「业务跑不通」根因诊断与修复路线

> 📅 2026-10-24 | 🔬 全部结论均来自实际执行验证（非静态阅读）
> 🎯 回应判断：训练/测试已跑通；规则引擎业务未跑通；UI 交互未做好

---

## 0. 一句话结论

**训练与测试是真跑通的；规则引擎是「骨架完整、血肉不通」。** 执行器的调度能力（拓扑排序、层内并行、超时、故障隔离、指标落库、版本迁移链）真实且有深度，但：

1. **节点之间的数据通道从未打通** —— 前后端 `data.inputs` 契约断裂，每个节点一执行就崩
2. **执行反馈从未送达用户** —— WS 连接竞态 + `batch` 事件前端不认 + 顶层状态谎报成功，四层叠加
3. **动作层的真实能力被注释掉** —— 键盘/鼠标/截屏节点返回 `success: true` 却什么都没做
4. **唯一的规则图是压测残留** —— 数据库里那张 `e2e_final` 是 18 组复制粘贴的平行链，没有业务闭环

## 2. 规则引擎业务跑不通：四层静默失败

这是本次诊断的核心。每一层都在掩盖下一层，所以从用户视角看就是「点了运行，什么都没发生，也没报错」。

### 第 1 层：输入数据契约断裂（**真凶**）

**前后端对 `data.inputs` 的理解完全不同：**

| 侧 | 位置 | 期望格式 |
|----|------|----------|
| 前端写入 | `webui/src/stores/ruleEngine/graph.ts:781` → `inputs: def.inputs` | **数组**（端口元数据：`[{name,type,label,description}]`） |
| 后端读取 | `backend/services/rule_engine/executor.py:822` → `inputs_config.items()` | **字典** `{端口名: {node_id, output}}` |

前端全项目**从未写入** `{node_id, output}`（`grep node_id webui/src` 无任何相关命中），
执行器也**从不从 `edges` 反推输入**（edges 只用于端口类型校验、拓扑排序、branch 分流三处）。

**实测证据（跑数据库里真实保存的 `e2e_final`）：**

```
场景1: 数据库里保存的 e2e_final（原样执行）
  顶层 status: completed
  node_started node=node_1780809616890_d
  node_failed  node=node_1780809616890_d  FAIL: 'list' object has no attribute 'items'
  ...（54 个节点全部同样报错）
  有输出的节点: 0 / 54
```

> 注意：**连没有输入端口的节点也崩**，因为 `inputs: []` 仍是 list，`[].items()` 同样抛 `AttributeError`。

**对照实验证明这就是根因：**

```
场景2: 前端格式（data.inputs = 端口元数据数组）
  a: FAIL: 'list' object has no attribute 'items'
  b: FAIL: 'list' object has no attribute 'items'

场景3: 改成执行器期望的 inputs 字典格式
  a: FAIL: 'list' object has no attribute 'items'      ← a 的 inputs 仍是 []
  b: FAIL: 输入校验失败: 缺少图片输入                    ← 越过输入解析，改报真实业务错误
```

节点 b 在场景 3 里**成功越过输入解析通道**，改报真实业务错误 —— 输入通道通了。

### 第 2 层：执行反馈被竞态丢弃

| 环节 | 位置 | 问题 |
|------|------|------|
| 后端触发 | `backend/routers/rule_engine.py:385+` | `background_tasks.add_task(run_execution)` —— 响应发出**之后**才开始跑 |
| 前端 | `webui/src/views/RuleCanvas.vue:2959-2966` | 先 `POST /execute` 拿 id，**再** `connectWebSocket(execId)` |
| WS 管理器 | `backend/services/rule_engine/websocket_manager.py:127-128` | `if not subscribers: continue` —— 无订阅者的消息**直接丢弃，无回放缓冲** |

毫秒级失败（本次就是）→ 所有节点事件在 WS 握手完成前就发完了 → **前端一条都收不到**。

### 第 3 层：`batch` 事件前端不认

| 侧 | 位置 | 内容 |
|----|------|------|
| 后端 | `websocket_manager.py:131-136` | 同一 16ms 窗口内 ≥2 条消息 → 包成 `{"type":"batch","messages":[...]}` |
| 前端 | `RuleCanvas.vue:1416` switch | 只有 `node_started` / `node_executed` / `node_failed` / `node_timeout` / `execution_progress` / `execution_complete` —— **无 `batch` 分支** |

批量事件被前端**整包丢弃**。用 `useWebSocket.ts` 全局搜 `batch` 亦无命中。

### 第 4 层：顶层状态谎报成功

`executor.py:532-536`：无论节点成败，返回的 `status` 恒为 `"completed"`。
节点级成败只体现在 `node_results` 里，而 UI 主要看顶层状态。

### 四层叠加的用户体验

```
点击「运行」
  → 后端 54 个节点全部崩溃（毫秒级）
  → 事件全在 WS 握手前发完，且被 batch 打包
  → 前端既没连上、又认不出 batch → 零反馈
  → API 返回 status: "completed"
  → 界面显示「执行完成」，日志面板空无一物
```

**这就是「规则引擎最实用，却根本没跑通业务」的机制解释。**

## 执行结果（2026-10-24 更新）

本诊断列出的断链已按 `docs/superpowers/plans/2026-10-24-规则引擎业务闭环与UI可用性改造.md` 完成改造。

| 诊断项 | 落地情况 |
|--------|---------|
| `data.inputs` 存的是端口元数据、后端当连线关系读 → 54 节点全崩 | ✅ 拆分为 `data.inputs`（元数据）+ `data.connections`（连线关系），executor `_resolve_inputs` 读 connections |
| BOOLEAN → TRIGGER 连线被丢弃，动作层不可达 | ✅ 端口矩阵单一事实源 + 补 `CONTROL → TRIGGER` |

| 键鼠/截屏/视频节点 0ms 谎报成功 | ✅ 接 `engine` 真实实现，失败显式抛 `ExecutorError` |
| 端到端闭环无验收脚本 | ✅ `scripts/e2e/rule_engine_business_flow.py` 退出码 0 |
