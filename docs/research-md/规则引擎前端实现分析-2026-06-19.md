## 1. 功能 Bug 详析

### BUG-1 [P0] Undo/Redo 移动方向错误

**文件**：`ruleEngine.ts:898-917`

**现象**：Redo 拖拽操作后节点位置不回到拖拽终点，而是回到拖拽起点。

**根因**：`applyHistoryEntry` 对 `move` 和 `groupMove` 类型始终使用 `entry.from`，无论当前是 undo 还是 redo。

```typescript
// ruleEngine.ts:898-917 (当前代码)
function applyHistoryEntry(entry) {
  if (entry.type === 'move') {
    node.position = { ...entry.from }  // ← BUG: redo 也用 from
  } else if (entry.type === 'groupMove') {
    const updates = entry.moves.map(m => ({ id: m.nodeId, position: { ...m.from } }))  // ← 同 BUG
    setNodesPositions(updates, false)
  }
}
```

**修复方向**：区分 undo/redo 方向。Undo 回到 `from`，Redo 回到 `to`。

**状态 (2026-06-19 修复)**：✅ `7ba1ddfb fix(rule-engine): 修 docs/research-md/2026-06-19 列出的 🔴 P0 三个 BUG` — `applyHistoryEntry` 接收 `direction: 'undo' | 'redo'` 参数,`direction === 'undo' ? from : to`。

```typescript
// 方案 A: applyHistoryEntry 接收方向参数
function applyHistoryEntry(entry, direction: 'undo' | 'redo') {
  const pos = direction === 'undo' ? entry.from : entry.to
  // ...
}

// 方案 B: undo/redo 各自传入目标 position
function undo() {
  historyIndex.value--
  const entry = historyStack.value[historyIndex.value]
  if (entry.type === 'move') applyMove(entry, entry.from)   // 回退
}
function redo() {
  historyIndex.value++
  const entry = historyStack.value[historyIndex.value]
  if (entry.type === 'move') applyMove(entry, entry.to)     // 前进
}
```

### BUG-2 [P1] 粘贴节点不显示选中态

**文件**：`RuleCanvas.vue:1315-1366`

**现象**：Ctrl+V 粘贴节点后，新节点在视觉上不显示选中高亮（outline），虽然数据中 `selected: true`。

**根因**：`handlePaste` 在新节点的 `data` 中设置了 `selected: true`，但从未调用 VueFlow 官方 `addSelectedNodes(newNodes)`。VueFlow 的选中态由内部 `selectedNodeIds` 管理，不依赖 `node.selected` 属性（何况 `nodes` 是 shallowRef + markRaw，属性变化不会触发渲染）。

```typescript
// RuleCanvas.vue:1315-1358 (当前代码)
const newNodes = srcNodes.map((n) => ({
  ...n,
  selected: true,            // ← 写了但没用，VueFlow 不读这个
  data: { ...(n.data || {}), id: newNodeId, selected: true }
}))

store.nodes = [...store.nodes, ...newNodes]
// ← 缺少: addSelectedNodes(新节点对应的 flowNode 数组)
```

**修复方向**：粘贴后 `nextTick` 调用 `addSelectedNodes`，让 VueFlow 内部 `selectedNodeIds` 同步。

**状态 (2026-06-19 修复)**：✅ `55533ec fix(rule-canvas): BUG-2 粘贴节点不显示选中态 — handlePaste 补 addSelectedNodes` — `store.nodes` 重新赋值后, `nextTick` 遍历 newNodes 调 `findNode(id)`, 收集 reactive flowNode 后 `addSelectedNodes` 一次性同步。

### BUG-3 [P1] 折叠按钮 class 名不匹配

**文件**：`useCogniFlowDrag.ts:103` vs `RuleNode.vue:33`

**现象**：节点右上角的折叠/展开按钮点击无响应，或触发拖拽而非切换折叠。

**根因**：d3-drag filter 排除列表中检查的是 `.node-expand-btn`，但 RuleNode.vue 中按钮实际 class 是 `.node-collapse-btn`：

```typescript
// useCogniFlowDrag.ts:103

// RuleNode.vue:33
<button class="node-collapse-btn" ...>  // ← 实际 class
```

由于 class 不匹配，d3-drag filter 返回 `true`，mousedown 被拖拽系统捕获，按钮的 `@click.stop` 失效。

**修复方向**：统一 class 名。将 filter 改为 `.node-collapse-btn`，或同时排除两者：

```typescript
if (target.closest('.node-expand-btn') || target.closest('.node-collapse-btn')) return false
```

**状态 (2026-06-19 修复)**：✅ `7ba1ddfb` — `useCogniFlowDrag.ts:104-105` 同时排除 `.node-collapse-btn` 和 `.node-expand-btn`。

### BUG-4 [P0] updateNodeConfig 不触发响应式更新

**文件**：`ruleEngine.ts:567-579`

**现象**：在 NodeConfigEditor 中修改配置值后，如果之后没有任何其他操作触发 `nodes` shallowRef 重新赋值，配置编辑器可能不会反映最新值（尤其折叠再展开后）。

**根因**：`nodes` 是 `shallowRef`，节点 `data` 是 `markRaw`。`updateNodeConfig` 内部 `node.data.config[key] = value` 是原地变异，但**不再调用 `triggerRef(nodes)`**。NodeConfigEditor 的 computed 链依赖 `store.nodeById` → `nodes.value`，由于 shallowRef 未被触发，整个 computed 链保持陈旧。

```typescript
// ruleEngine.ts:567-579
function updateNodeConfig(nodeId: string, key: string, value: VariableDefaultValue) {
  const node = nodes.value.find(n => n.id === nodeId)
  if (node?.data) {
    node.data.config[key] = value
    // 不再 triggerRef(nodes) ← 问题根源
  }
}
```

**修复方向**：配置变更后需触发 NodeConfigEditor 能感知到的响应式信号。两个方案：

- **方案 A（轻量）**：恢复 `triggerRef(nodes)`，但只在 NodeConfigEditor 可见时触发（避免拖拽等场景的全图 diff）
- **方案 B（精细）**：单独维护一个 `configVersion` shallowRef，`updateNodeConfig` 后 `triggerRef(configVersion)`，NodeConfigEditor 的 computed 依赖它

**状态 (2026-06-19 修复)**：✅ `7ba1ddfb` — 走方案 B。`ruleEngine.ts:166` 加 `_configVersion = shallowRef(0)`, `updateNodeConfig` 后 `_configVersion.value++`, 通过 store 暴露 `configVersion`; `NodeConfigEditor.vue:320` 显式 `void store.configVersion` 建响应式依赖。

## 2. 性能瓶颈详析

### PERF-1 [P0] nodeById computed 全量重建 Map

**文件**：`ruleEngine.ts:226-232`

**问题**：`nodeById` 是 `computed`，每次 `nodes.value`（shallowRef）被重新赋值时都会重建整个 Map。以下操作均会触发重建：

- `createNode` / `removeNode` / `removeNodes`
- `handlePaste` (追加节点)
- `handleCut` (删除节点)
- `undo` / `redo` (snapshot 路径)
- `saveGraph` / `loadGraph`
- `handleNodesChange` (meaningful 路径)

100 节点场景：每次重建 100 次 Map.set + 1 次 Map 构造 ≈ 0.05ms，但在高频操作（快速粘贴/撤销）中会累积。

**修复方向**：改用增量维护（类似 `_connectedHandleIndex` 的模式），或在 `nodes.value` 变化时用 diff 算法只增删变更项。简单方案：用 `shallowRef<Map>` + 手动维护。

---

### PERF-2 [P0] baseLodLevelMap 缓存命中率低

**文件**：`ruleEngine.ts:288-347`

**问题**：短路缓存检查 `nodesRef === nodes.value`，但 `nodes` 是 shallowRef，以下操作都会创建新数组引用导致缓存失效：

- `createNode`: `nodes.value = [...nodes.value, markRaw(newNode)]`
- `removeNode`: `nodes.value = nodes.value.filter(...)`
- `handlePaste`: `store.nodes = [...store.nodes, ...newNodes]`
- `handleCut`: `store.nodes = store.nodes.filter(...)`
- `undo/redo`: snapshot 路径 `nodes.value = JSON.parse(...)`

每次缓存失效 → 全量遍历 N 节点重建 Map → 对 200 节点场景约 0.1ms。虽然单次开销不大，但在快速连续操作时可能叠加。

**修复方向**：将缓存 key 从引用相等改为长度 + 首尾 id 快速校验，或改用增量维护。

---

### PERF-3 [P1] handleSelectionEnd DOM 遍历触发布局回流

**文件**：`RuleCanvas.vue:1521-1536`

**问题**：框选结束时，使用 `querySelectorAll('.vue-flow__node[data-id]')` + `getBoundingClientRect()` 做 AABB 命中测试。`getBoundingClientRect()` 会强制浏览器同步计算布局（layout reflow），200 个节点 = 200 次回流。

**当前影响**：框选结束仅触发一次，非持续瓶颈。但 200 节点场景下可能造成 5-15ms 的帧卡顿。

**修复方向**：
- **方案 A**：利用 `IntersectionObserver` 预缓存节点位置（复杂度高）
- **方案 B**：改用 `node.computedPosition` + 已知节点尺寸做纯数学计算（无 DOM 依赖，零回流）
- **方案 C**：批量 `getBoundingClientRect` 前先读一次容器 rect，减少回流次数（浏览器会合并同一帧内的多次读取）

### PERF-4 [P0] useEdgePathUpdater 使用 O(N) 查找

**文件**：`useEdgePathUpdater.ts:93,116-117`

**问题**：`start()` 函数中多处使用 `store.nodes.find(n => n.id === id)` 进行 O(N) 线性查找：

```typescript
// useEdgePathUpdater.ts:93
const node = store.nodes.find(n => n.id === id)  // O(N)

// useEdgePathUpdater.ts:116-117
const sourceNode = sourceMoving ? store.nodes.find(n => n.id === edge.source) : null
const targetNode = targetMoving ? store.nodes.find(n => n.id === edge.target) : null
```

拖动 5 个节点时，每个节点 1 次查找 + 每条 incident edge 2 次查找。5 节点 × 3 边 = 5 + 30 = 35 次 O(N) 查找。

**修复方向**：改用 `store.nodeById.get(id)` O(1) 查找，与 RuleCanvas.vue 中其他路径保持一致。

**状态 (2026-06-19 修复)**：✅ `b38fbf4 perf(rule-canvas): PERF-4 edgePathUpdater O(N)→O(1)` — `start()` 函数 3 处 `store.nodes.find` 全改 `store.nodeById.get(id)`, 拖动期间 0 次线性查找, 单帧省 ~0.1ms。

### PERF-5 [P1] saveHistory 全量快照序列化

**文件**：`ruleEngine.ts:813-848`

**问题**：每次 `saveHistory()` 都调用 `cloneForHistory(nodes.value)` 遍历所有节点做 JSON 兼容序列化。100 节点场景约 0.5-1ms。

触发频率高：
- `createNode` / `removeNode` / `removeNodes`
- `addEdge` / `removeEdge` / `removeEdges`
- `handlePaste` (1 次)
- `handleCut` (1 次)
- `loadGraph` (1 次)

**修复方向**：
- 对高频操作（如 `addEdge`）使用增量 history entry（类似 `move`/`groupMove`）
- 或延迟快照：连续快速操作合并为 1 次快照

### PERF-6 [P1] handleCopy 序列化 VueFlow 内部数据

**文件**：`RuleCanvas.vue:1236-1237`

**问题**：`handleCopy` 直接 `JSON.stringify(selected)` 序列化 VueFlow GraphNode 对象。这些对象包含大量 VueFlow 内部字段（`dragging`, `dimensions`, `handleBounds`, `internals` 等），序列化时被忽略但浪费 CPU 做属性遍历。100 节点复制时影响约 1-2ms。

**修复方向**：只序列化业务字段（同 `cloneForHistory` 的策略），减少序列化体积和 CPU 开销。

### PERF-7 [P2] filteredCategories 搜索实时重算

**文件**：`RuleCanvas.vue:909-931`

**问题**：`filteredCategories` computed 在每次搜索输入变化时重新过滤所有节点定义。当前节点定义数量较少（~20），影响不大。但如果节点定义数量增长到 100+，每次按键的过滤开销会增加。

**修复方向**：对 `nodeSearchQuery` 加 150ms debounce，减少中间态重算。

### PERF-8 [P2] connectedHandleIndex 全量重建

## 3. 设计隐患

### DESIGN-2 选中状态双源

**文件**：`RuleCanvas.vue` + `ruleEngine.ts`

**问题**：节点选中态有两个来源：
1. VueFlow 内部 `selectedNodeIds`（通过 `addSelectedNodes`/`removeSelectedNodes` 管理）
2. `store.nodes[i].selected` 属性（shallowRef + markRaw，实际已废弃但仍被部分代码引用）

---

### DESIGN-3 shallowRef + markRaw 的响应式盲区

**文件**：`ruleEngine.ts` 全局

**问题**：项目大量使用 `shallowRef` + `markRaw` 优化性能，但代价是每次内部属性变更都需手动 `triggerRef`。当前有 14 处 `triggerRef` 调用，遗漏任何一处都会导致 UI 不更新（BUG-4 即为典型）。此外，`triggerRef(nodes)` 在某些路径（如 drag-stop）被有意跳过（`skipTrigger=true`），增加了正确性推理的难度。

**建议**：
- 建立文档化的 `triggerRef` 调用清单，标注每处的触发条件
- 考虑引入 `watchEffect` + dirty flag 模式，让触发条件自动推断
- 或对 `nodes` 使用 `ref` + 自定义 shallow equals 来减少手动管理

---

### DESIGN-4 自研拖动与 VueFlow 拖动并存

**文件**：`useCogniFlowDrag.ts` + `RuleCanvas.vue`

**问题**：`<VueFlow :nodes-draggable="false">` 禁用了 VueFlow 内部拖动，改由 `useCogniFlowDrag` (d3-drag) 接管。但 VueFlow 的 NodeWrapper 内部仍有 `useDrag` hook（只是被 `nodesDraggable` 守卫跳过），两套拖动逻辑共存增加了维护成本。

**具体隐患**：
- VueFlow NodeWrapper 的 `onClick` 仍在处理选中（与 `handleNodeClick` 有微妙交互）
- d3-drag filter 需要手动维护排除列表（Handle、按钮等），VueFlow 升级后可能新增交互元素
- 拖动期间 DOM 直写 `el.style.transform`，dragEnd 后清空让 VueFlow 接管，存在一帧闪烁风险

**建议**：长期考虑 fork VueFlow 的 NodeWrapper，去掉内部 useDrag，彻底消除双拖动系统。
