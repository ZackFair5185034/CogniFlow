## 1. 摘要（TL;DR）

### 1.1 Ctrl 增量框选当前现象

按住 Ctrl 框选第二批节点，**期望**：旧选中保留 + 新命中追加。**实际**：旧选中被清空，最终只剩本次框中的节点（退化成普通框选）。

### 1.2 根因（一句话）

`VueFlow` 模板属性 `:selection-key-code="true"` 让框选模式永远激活，但**没有配置** `:multi-selection-key-code`。VueFlow 内部 `Pane.onPointerDown` 在框选开始时根据 `multiSelectionKeyPressed` 决定是否调用 `removeSelectedElements()`——由于该属性永远是 `false`，VueFlow 在按下鼠标的瞬间就把所有旧选中通过 `flowNode.selected = false` 清掉了。等到 `@selection-start` 触发时再读 `multiSelectKeyPressed.value` 锁定 `selectionAdditive` 已经晚了一拍——`handleSelectionEnd` 里读到的 `getSelectedNodes.value` 是空的，加选退化成替换。

### 1.3 修复方向（一句话）

给 `<VueFlow>` 加上 `:multi-selection-key-code="['Control', 'Meta', 'Shift']"`，让 VueFlow 内部 `multiSelectionKeyPressed` 在按住修饰键时为 `true` → `Pane.onPointerDown` 跳过 `removeSelectedElements()` → `handleSelectionEnd` 才能读到旧选中。同时把 `handleSelectionStart` 的 `selectionAdditive` 锁定换成 `(event.sourceEvent as PointerEvent).ctrlKey/metaKey/shiftKey` 兜底（同源 PointerEvent 比独立的 `keydown/keyup` ref 更可靠）。

### 1.4 其它发现摘要

| 类别 | 数量 | 严重度分布 |
|---|---|---|
| 框选/选中相关 bug | 5 | 🔴×1 / 🟡×2 / 🟢×2 |
| 拖动相关缺陷 | 3 | 🟡×2 / 🟢×1 |
| 坐标系/状态一致性 | 4 | 🟡×3 / 🟢×1 |
| 性能潜在热点 | 6 | 🟡×3 / 🟢×3 |
| 内存/生命周期 | 2 | 🟢×2 |

详见 §4, §5。

```
用户按下鼠标在画布空白处
  ↓
VueFlow Pane.onPointerDown
  ├─ selectionKeyPressed.value = true              ← 因 :selection-key-code="true"
  ├─ ⚠ if (!multiSelectionKeyPressed.value)       ← multi-selection-key-code 未配置, 永远 false
  │     removeSelectedElements()                   ← ⚠⚠⚠ 这里把所有旧选中清掉了
  │       └─ flowNode.selected = false × N
  │       └─ emit nodesChange[select:false] × N    ← 被 isBatchDragging 跳过(store 没改)
  │                                                  但 flowNode.selected 内部已是 false
  ├─ userSelectionRect.value = { x, y, ... }
  └─ emits.selectionStart(event)
      ↓
RuleCanvas.handleSelectionStart(event)
  ├─ isSelectionDragging.value = true
  ├─ isBatchDragging.value = true
  ├─ store.setSelectionBoxActive(true)
  ├─ selectionAdditive = multiSelectKeyPressed.value
  │   ⚠ multiSelectKeyPressed 是 RuleCanvas 自己挂 keydown/keyup 维护的 ref
  │   ⚠ 锁定时机晚于 VueFlow removeSelectedElements()
  ├─ isAdditiveSelection.value = selectionAdditive  ← 视图角标用
  ├─ userSelectionRect.value = null                 ← 阻断 VueFlow Pane onPointerMove 跑 getNodesInside
  └─ customSelectionRect.value = { x, y, 0, 0 }

mousemove × N 帧 (60Hz)
  ↓
.flow-container @mousemove → handleCanvasMouseMove
  ├─ 算容器坐标 (减 flowContainer.getBoundingClientRect)
  ├─ customSelectionRect.value = { x, y, w, h }    ← 走响应式但 0 vue-flow 重算
  └─ lastMousePos.value = { x: cx, y: cy }          ← 容器坐标 (注: 与 pan 分支屏幕坐标冲突, §4 BUG-CFL-3)

mouseup
  ↓
VueFlow Pane.onPointerUp → emits.selectionEnd
  ↓
RuleCanvas.handleSelectionEnd(event)
  ├─ 清状态 (isSelectionDragging/isBatchDragging/customSelectionRect/...)
  ├─ 容器坐标算 finalRect
  ├─ DOM 查询 .vue-flow__node[data-id]
  │   ⚠ 受 :only-render-visible-elements="true" 影响, 视口外节点不在 DOM (§5.2 PERF-2)
  ├─ getBoundingClientRect AABB → hitIds
  ├─ if (isAdditive) {
  │     finalIds = new Set(hitIds);
  │     for (n of getSelectedNodes.value) finalIds.add(n.id)
  │     ⚠⚠⚠ 这里读到的是空的! VueFlow removeSelectedElements 已经清空了
  │   }
  └─ syncSelectionToStoreNodes(finalIds) → addSelectedNodes / removeSelectedNodes
```

## 3. Ctrl 增量框选 Bug 链路根因（核心）

### 3.1 🔴 BUG-CFL-1（核心）：`multi-selection-key-code` 未配置，VueFlow 内部清空旧选中

**位置**:
- 配置缺失: `RuleCanvas.vue:376–414` 的 `<VueFlow ...>` props（无 `multi-selection-key-code`）
- 修复触点: `:selection-key-code="true"` 同行附近

**VueFlow 1.x 源码行为**（vue-flow-core.mjs Pane.onPointerDown 关键片段）:

```js
function onPointerDown(event) {
  // 进入 selection 模式判定: selectionKeyPressed 或 selectionOnDrag 等
  if (selectionKeyPressed.value || ...) {
    // 关键: 仅当未按修饰键时清空旧选中
    if (!multiSelectionKeyPressed.value) {
      removeSelectedElements()   // ← 把所有 flowNode.selected = false
    }
    // 设上初始 rect、emit selectionStart
    userSelectionRect.value = { x, y, startX: x, startY: y, ... }
    emits.selectionStart(event)
  }
}
```

VueFlow 内部 `multiSelectionKeyPressed` 来自 `useKeyPress(multiSelectionKeyCode)`：
- 默认值 `multiSelectionKeyCode = 'Meta'`（VueFlow 1.x 默认）
- 如果传 `true` 永真，传字符串监听对应按键，传 `null` 永假

**事实**: 项目里 `<VueFlow>` 完全没传 `multi-selection-key-code`，VueFlow 走默认 `'Meta'`：
- macOS 用户按 ⌘ 键时 `multiSelectionKeyPressed = true` → 不清空（碰巧能用）
- **Windows/Linux 用户按 Ctrl 键时 `multiSelectionKeyPressed = false`** → 清空旧选中 → BUG！
- **任何平台按 Shift 都失效**

**调用时序证据**（按帧排）:

| 帧 | 事件 | 结果 |
|---|---|---|
| t0 | 用户按住 Ctrl 拖框 | KeyboardEvent → `multiSelectKeyPressed.value = true` |
| t1 | mousedown 在空白处 | VueFlow `Pane.onPointerDown` 触发 |
| t2 | onPointerDown 内 | `multiSelectionKeyPressed = false`（默认走 Meta）→ 清空旧选中 |
| t3 | onPointerDown 内 emit | `selectionStart` |
| t4 | `handleSelectionStart` 跑 | `selectionAdditive = true`（ref 锁对了，但晚了） |
| t5 | mousemove × N | 自绘框、`customSelectionRect` 更新 |
| t6 | mouseup → `selectionEnd` | `handleSelectionEnd` 跑 |
| t7 | 读 `getSelectedNodes.value` | **空数组**（已被 t2 清光） |
| t8 | `isAdditive=true` 分支 | `finalIds = hitIds`（旧的没合上） |
| t9 | `syncSelectionToStoreNodes(finalIds)` | 用户只看到本次新框中的节点 ← BUG |

**为什么 `isBatchDragging.value = true` 没救场?**

`handleSelectionStart` 里设 `isBatchDragging = true`，让 `handleNodesChange` 直接 return。这只能阻止 store 的 `select` change 被处理——**但 VueFlow 内部 `flowNode.selected = false` 是直接 mutate reactive 对象**，不经过 `applyVueFlowNodeChanges`，所以 `isBatchDragging` 拦截不到。`getSelectedNodes` 是 VueFlow 内部 computed，直接读 `flowNode.selected`，等于已经是 false 了。

**修复方案**（详 §6.1）:

```vue
<VueFlow
  ...
  :selection-key-code="true"
  :multi-selection-key-code="['Control', 'Meta', 'Shift']"  ← 新增
  ...
>
```

> VueFlow 1.x 的 `selection-key-code` 与 `multi-selection-key-code` 都接受 `string | string[] | boolean | null`，传数组时任意一个按下都会激活。

### 3.2 🟡 BUG-CFL-2：`multiSelectKeyPressed` ref 与 VueFlow 内部状态分裂

**位置**: `RuleCanvas.vue:1455–1472`

```ts
const multiSelectKeyPressed = ref(false)
function onKeyDown(e: KeyboardEvent) {
  if (e.ctrlKey || e.metaKey || e.shiftKey) multiSelectKeyPressed.value = true
}
function onKeyUp(e: KeyboardEvent) {
  if (!e.ctrlKey && !e.metaKey && !e.shiftKey) multiSelectKeyPressed.value = false
}
onMounted(() => {
  window.addEventListener('keydown', onKeyDown)
  window.addEventListener('keyup', onKeyUp)
  window.addEventListener('blur', onKeyUp)  // ⚠ blur 事件不是 KeyboardEvent
})
```

**问题 1（类型隐患）**: `window.addEventListener('blur', onKeyUp)` 时，事件参数是 `FocusEvent`，访问 `e.ctrlKey/metaKey/shiftKey` 是 `undefined`（实际行为）但触发 `!undefined === true` 让 `if` 通过。运气好达到清零目的，但 TS 严格模式应警告。

**问题 2（同源分裂）**: 项目里维护了**两套**修饰键状态：
- 自己挂的 `multiSelectKeyPressed`（用于 `handleSelectionStart` 锁定 `selectionAdditive`）
- VueFlow 内部 `useKeyPress(multiSelectionKeyCode)`（决定 `removeSelectedElements` 是否执行）

修复 BUG-CFL-1 后，两套状态会指向同样的修饰键（Ctrl/Meta/Shift），但仍是两个独立的 ref——可能因事件顺序、窗口失焦时机产生微妙差异。**建议**：消除自维护 ref，改读 `event.sourceEvent.ctrlKey/metaKey/shiftKey` 直接从框选 PointerEvent 拿。

**修复方案**（详 §6.2）: 在 `handleSelectionStart` 里直接读 `event.sourceEvent`，移除整套自挂 keydown/keyup 监听。

### 3.3 🟡 BUG-CFL-3：`lastMousePos` 在 pan 分支与框选分支坐标系冲突

**位置**: `RuleCanvas.vue:804`, `2044`, `2084`

```ts
// 定义
const lastMousePos = ref({ x: 0, y: 0 })

// pan 分支
function handleCanvasMouseDown(event: MouseEvent) {
  if (event.button === 1 || (event.button === 0 && event.altKey)) {
    isPanning.value = true
    lastMousePos.value = { x: event.clientX, y: event.clientY }   // ⚠ 屏幕坐标
    ...
  }
}

// 框选分支
function handleCanvasMouseMove(event: MouseEvent) {
  if (isSelectionDragging.value && selectionStartPos) {
    const cx = event.clientX - offsetX
    ...
    lastMousePos.value = { x: cx, y: cy }   // ⚠ 容器坐标
    ...
  }
}

// 复制粘贴用
async function handlePaste(event?: MouseEvent) {
  ...
  const screenX = event?.clientX ?? lastMousePos.value.x   // ⚠ 期望屏幕坐标
  ...
}
```

**问题**: 同一个 ref，三个地方写入坐标系不同：
- pan 写**屏幕**坐标
- 框选写**容器**坐标
- handlePaste 期望**屏幕**坐标（用 `event?.clientX ?? lastMousePos.value.x` 兜底）

如果用户先做框选再用快捷键 Ctrl+V（无 MouseEvent，走 lastMousePos）：粘贴位置会偏离容器偏移量。

**修复方案**: 拆成两个 ref（`lastMousePosScreen` + `lastMousePosContainer`），或统一一种坐标系（推荐屏幕坐标，避开容器 resize 时的失真）。

### 3.4 🟢 BUG-CFL-4：微小框选 (w<3 && h<3) 不清空旧选中也不触发 pane-click

**位置**: `RuleCanvas.vue:1511–1514`

```ts
if (containerRect.width < 3 && containerRect.height < 3) {
  return  // ⚠ 直接 return, 不清旧选中
}
```

**问题**: 用户在空白处轻点（< 3px），期望：
- 普通：清空旧选中（macOS Finder 行为）
- 加选：保留旧选中

实际：什么都不做。如果用户的微抖动触发了 VueFlow 内部的 `removeSelectedElements`（BUG-CFL-1 修后），那么本就没旧选中可清。但如果 BUG-CFL-1 修复方案让 VueFlow 不再在 mousedown 清空（加了 multi-selection-key-code），普通微小框选就会**保留旧选中**——与桌面应用约定不符。

**修复方案**: 微小框选若 `!isAdditive` 走 `syncSelectionToStoreNodes(new Set())` 清空选中。

### 3.5 🟢 BUG-CFL-5：`handleSelectionEnd` 兜底分支用空 Set 清空选中过激

**位置**: `RuleCanvas.vue:1497–1501`

```ts
if (!start || !end) {
  syncSelectionToStoreNodes(new Set())   // ⚠ 加选模式下也清空旧选中
  return
}
```

**问题**: 如果 `selectionStartPos` 因异常路径丢失（如 mousedown 在 VueFlow 内部被吞），这里强制清空选中。但用户的意图是"框选未发生" → 应保留旧选中。

**修复方案**: 兜底分支应直接 return，不动选中。

## 4. 其它设计缺陷与功能性问题

### 4.1 拖动相关

#### 🟡 DRAG-1: 拖动未选中节点时，bypass 修饰键 → Ctrl+拖未选 = 替换式选中

**位置**: `useCogniFlowDrag.ts:146–177`

```ts
if (el.classList.contains('selected')) {
  allEls = Array.from(document.querySelectorAll('.vue-flow__node.selected'))
} else {
  // 拖未选中节点
  const additive = src.ctrlKey || src.metaKey || src.shiftKey
  if (additive) {
    options.addSelectedNodes([targetFlowNode])  // ✓ 保留旧选中 + 加新
  } else {
    options.removeSelectedNodes(currentlySelected)  // ✓ 清空 + 只选新
    options.addSelectedNodes([targetFlowNode])
  }
}
```

**问题**: 流程正确，但 `additive` 分支只是把 target 加入选中，**没把 target 加到 `allEls`** → 拖动只移动 target 一个节点（旧选中节点不跟随）。

期望行为（macOS/Windows）：
- 拖未选 → 只拖 target（清旧选中）✓ 当前代码正确
- Ctrl+拖未选 → 把 target 加入选中集，**整个新集合一起拖动**

修复方案：`additive` 分支补 `allEls = [...currentlySelected.map(getEl), el]`。

#### 🟡 DRAG-2: `isClick` 阈值 5px 在高 DPI/平滑触控板下偏大

**位置**: `useCogniFlowDrag.ts:217`

```ts
if (Math.abs(dxScreen) > 5 || Math.abs(dyScreen) > 5) {
  isClick = false
}
```

**问题**: 触控板平滑滚动产生 1-3px 微抖动 → 误判拖动；但 5px 偶尔会让快速移动的鼠标在拖动开始时被误判为点击。

修复方案：拆 X/Y 用 hypot，阈值降到 3px；或用 `pointerType === 'touch'` 判断设备类型。

#### 🟢 DRAG-3: 路径 B 拖动期间，VueFlow 内部 `flowNode.position` 不变 → MiniMap 不跟手

**位置**: `useCogniFlowDrag.ts:209–250`

拖动期间直接改 `el.style.transform`，**没改 `flowNode.position`**（直到 dragEnd 才同步）。MiniMap 节点位置基于 `flowNode.computedPosition`（依赖 `position`） → 拖动过程中 MiniMap 节点不动。

#### 🟡 COORD-2: pan 直写 transform 与 setViewport 之间存在时序窗口


#### 🟢 COORD-4: `screenToFlowCoordinate` 输入需 `clientX - containerRect.left`，handleDrop 用了，quickAddNode 没用

## 5. 性能优化建议

### 5.1 🟡 PERF-1: 框选命中检测的 DOM 查询 O(N×getBoundingClientRect)

**当前**: `handleSelectionEnd` 调 `container.querySelectorAll('.vue-flow__node[data-id]')` 拿所有可见节点 DOM，再 N 次 `getBoundingClientRect()`。

**复杂度**: O(N) querySelectorAll + O(N) bounding rect 读取（每次都 force layout）→ 80 节点约 5-10ms。

**优化方案**:
1. **方案 A（最简）**: 用 `Element.getBoundingClientRect()` 是同步 layout 操作；改成在拖框开始时一次性读取所有可见节点的 rect（拖动期间节点位置不变），缓存到 Map<id, rect>。结束时只做容器 rect 偏移计算（无 layout）。
2. **方案 B（更优）**: 用 store 维护的 `nodeById` + `node.position` + `node.dimensions`（VueFlow 计算并回写）算画布坐标 AABB，配合 viewport 反变换框选 rect → 0 DOM 查询。
3. **方案 C（极致）**: 节点空间索引（RBush / KD-Tree）→ 框选 O(log N + K)，K 为命中数。200+ 节点收益明显。

> Phase 17.5 切到 DOM 命中是为了规避 `store.dimensions` 不回写的问题（fallback 200x80 偏小）。可以验证 VueFlow 1.x 是否回写 `flowNode.dimensions`（实际是 `node.dimensions = { width, height }` 在挂载后），如果是就走方案 B。

### 5.2 🟡 PERF-2: `only-render-visible-elements` 与 DOM 命中检测互斥

**位置**: `RuleCanvas.vue:395`

```vue
:only-render-visible-elements="true"
```

**问题**: 该属性让视口外节点不渲染（性能优化）；但 §5.1 的 DOM 命中检测只能选到**当前可见**节点。框选拉得很大覆盖视口外节点时，那些节点**不会被选中**。

**典型场景**: 用户缩放到 0.3，拖框覆盖整张图 → 期望全选；实际只选中视口可见节点。

**修复方案**: 与 PERF-1 方案 B/C 配合，用 store 数据做命中检测，不依赖 DOM。

### 5.3 🟡 PERF-3: `handleCanvasMouseMove` 框选分支 60Hz reflow

详 §4.3 COORD-1。

### 5.4 🟢 PERF-4: `historyStack` snapshot 深拷贝代价

**位置**: `ruleEngine.ts:802–821 (cloneForHistory)`

`saveHistory` 走 cloneForHistory（每节点 spread + data spread + position spread）；`applyHistoryEntry` 的 snapshot 分支用 `JSON.parse(JSON.stringify(...))` 整图。

**测试时机**: 200 节点 → cloneForHistory 约 5ms（一次），JSON.parse 约 15ms（单次操作可接受）。

**优化方案**:
1. **结构性共享**：仅克隆变更字段，未变更引用复用（Immer / structuredClone + 增量）。但实施成本高，目前 maxHistorySize=20，内存占用尚可（200 节点 × 20 entry × 1KB ≈ 4MB），不急于优化。
2. **更激进的 move/groupMove**：让连续修改单字段（如 updateNodeConfig）也走轻量 entry，而不是 snapshot。

### 5.5 🟢 PERF-5: `handleNodesChange` 拆解循环 O(changes)

**位置**: `RuleCanvas.vue:1934–1948`

```ts

  if (c.type === 'position' && c.dragging === true) continue
  if (c.type === 'select' && isSelectionDragging.value) continue
```

### 5.6 🟢 PERF-6: `Set<string>` 序列化 key 拼接热点

**位置**: `ruleEngine.ts:167–185 (_indexAddEdge/_indexRemoveEdge)`

```ts

```

每次 addEdge/removeEdge 调用 4 次模板字面量拼接。100+ 边时 loadGraph 阶段大约 400 次拼接，可忽略。

### 5.7 🟢 PERF-7: 标尺（ruler）渲染缺失节流

`RuleCanvas.vue:3375+` 定义了 ruler CSS 但未见 ruler-mark 的动态生成代码。若现状是 `v-for` 渲染 N 个 mark 跟随 viewport，每帧 patch 就是热点。**待审计**：搜索 `ruler-mark` 渲染来源，如果是模板循环且依赖 viewport.zoom，强烈建议 Canvas/DOM-直写。

### 5.8 🟢 PERF-8: 节点壳 `RuleNode.vue` v-memo 命中验证

|---|---|---|---|---|
| 屏幕坐标 (client) | px | 浏览器视口左上角 | `event.clientX/Y`, `getBoundingClientRect()` | 鼠标事件 |
| 容器坐标 (pane-relative) | px | `flowContainer` 元素左上角 | `clientX - container.left` | `customSelectionRect`, VueFlow `userSelectionRect` |
| 画布坐标 (flow / renderer) | px / zoom | 画布原点（节点 position 字段） | `(container - viewport.x/y) / zoom` | `node.position`, `getNodesInside` 输入 |

转换公式：
- `container = client - flowContainer.left/top`
- `flow = (container - viewport.x/y) / viewport.zoom`

VueFlow API:
- `screenToFlowCoordinate(point)`: 屏幕 → 画布
- `flowToScreenCoordinate(point)`: 画布 → 屏幕
- `pointToRendererPoint(point, viewport)`: 容器 → 画布（内部）

### 8.3 状态机：框选 / 拖动 / 平移 互斥

```
Idle
  ├─[mousedown on .vue-flow__node, no Alt/Mid]→ Dragging (useCogniFlowDrag)
  ├─[mousedown on .vue-flow__pane, Alt or Mid]→ Panning  (handleCanvasMouseDown)
  └─[mousedown on .vue-flow__pane, no modifier]→ Selecting (VueFlow Pane.onPointerDown)
                                                  ↓
                                                  Ctrl/Meta/Shift？
                                                    ├─ 是 → Additive Selecting
                                                    └─ 否 → Replace Selecting
```
