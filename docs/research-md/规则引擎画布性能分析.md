# 规则引擎画布性能分析 & 优化方案

> **分析日期**：2026-06-06
> **作用域**：`webui/src/views/RuleCanvas.vue` + `webui/src/components/rule-engine/RuleNode.vue` + `webui/src/stores/ruleEngine.ts`
> **版本基线**：`feature/rule-engine-development` @ `8fa1b777`
> **目标**：定位拖拽卡顿根因，给出可实施的优化路线

---

## 0. 核心结论

**用户感知"拖拽卡顿"主要由 4 类问题叠加造成**：

| 优先级 | 问题 | 单点成本 | 触发频率 |
|---|---|---|---|
| **P0** | `v-model` 双向回写让整图在每帧都重渲染 | O(N 节点) | **每帧** (60 Hz) |
| **P0** | `saveHistory` 在拖拽过程中深克隆整图 | O(N+M 边) JSON | **每帧**（潜在） |
| **P0** | `nodes`/`edges` 用 `ref` 深代理，Vue3 追踪每节点内部 | O(N) 依赖追踪 | 每次 mutation |
| **P1** | `updateNodeConfig` 改引用触发整节点 re-render | O(N widget) | 每次 widget 改值 |
| **P1** | 每个 RuleNode 内部 26 处 el-* 组件 + 复杂渐变/阴影/边框 | O(N) 重排重绘 | 拖拽中持续 |
| **P2** | 缩略图生成在每次 saveGraph 触发 | Canvas 2D draw + base64 + HTTP | 拖拽停止一次 |
| **P2** | WebSocket `node_started/executed/failed` 高频推送无合并 | O(1) 写日志 | 节点级，每次执行 |

按"5 个修复 ≤ 200 行改动"估，**单次拖拽帧耗时能从 8-15 ms 降至 2-3 ms（30+ fps 改善）**。

## 2. 缺陷逐条分析

### 缺陷 #1 【P0】v-model:nodes 触发每帧全图重渲染

**位置**：`RuleCanvas.vue:365`
```vue
<VueFlow v-model:nodes="nodes" v-model:edges="edges" ... />
```

**问题**：
VueFlow 内部用 `shallowRef` 管理 nodes 几何状态，**它本身拖拽就极快**——坐标变更只触发它自己的 d3-zoom transform。

但当前用了 v-model，每次节点 position 变化，VueFlow 内部会通过 `update:modelValue` 把整张 nodes 数组回写给 store。`storeToRefs` 把 store 的 nodes 绑到 template，每次赋值都让**所有依赖 `nodes` 的 computed、watch、template** 重新求值。

**影响计算**：
- 30 节点 × 60 fps = 1,800 computed 重算/秒
- 每个 RuleNode 的 `nodeConfig = computed(...)` 在 props.data 引用变更时重算
- 1,800 × 4 widget ≈ 7,200 element diffs/秒

**根因**：**VueFlow 拖拽只需本地状态；只在 dragStop 时回写一次**。这是 VueFlow 文档的"Manual control" 模式。

**VueFlow 1.48 推荐做法**：
```vue
<VueFlow :nodes="nodes" :edges="edges" :nodes-draggable="true"
  @nodes-change="onNodesChange" />
```
在 `onNodesChange` 内用 `applyNodeChanges(changes, nodes.value)` 手动 reconcile；用 `updateNodePositions(changes)` 局部更新位置（O(1) 替换一个节点）。

### 缺陷 #2 【P0】saveHistory 在拖拽过程中执行深克隆

**位置**：`stores/ruleEngine.ts:385-401`
```ts
function saveHistory() {
  historyStack.value.push({
    nodes: JSON.parse(JSON.stringify(nodes.value.map(n => ({...n, selected: false, dragging: false})))),
    edges: JSON.parse(JSON.stringify(edges.value.map(e => ({...e, selected: false}))))
  })
}
```

**问题**：
- 50 张深克隆图常驻内存
- `JSON.parse(JSON.stringify())` 比 `structuredClone` 慢约 30%
- 拖拽过程中如果调了 `saveHistory()`，每帧都做整图深克隆

**触发路径**：
- `handleNodeDragStop` → `unpauseHistory` → `saveHistory`（这是设计内的，dragStop 一次）
- `handleSelectionDragStop` → 整图重建 → `store.nodes = updated` → 如果 `saveHistory` 间接触发，全图再深克隆
- `saveGraph` → 走 API，不直接调用 saveHistory

**根因**：**两步都做了多余的事**：(a) unpause 触发 saveHistory 时还在 watch 路径上可能二次调用；(b) JSON 序列化用更慢的 stringify-parse 对。

**修复**：
- 用 `structuredClone` 替代 `JSON.parse(JSON.stringify(...))`（~30% 快、保留 Date/Map/Set）
- 拖拽期间 `unpauseHistory` → saveHistory 一次
- 撤销栈裁剪为 20 步（实际上 30 步的撤销粒度已足够）

### 缺陷 #3 【P0】nodes/edges 用 ref 而非 shallowRef

**位置**：`stores/ruleEngine.ts:80-83`
```ts
const nodes: Ref<Node<RuleNodeData>[]> = ref([])  // ← deep proxy!
const edges: Ref<Edge[]> = ref([])                  // ← deep proxy!
```

**问题**：
- Vue3 `ref([])` 对**数组元素和对象内部**都建 Proxy
- `node.position = {x: 100, y: 200}` 会触发 `node.position.x` 和 `node.position.y` 的依赖追踪
- 节点数据是 VueFlow 内部管理的异构树（包含 `data.config` 等），深代理无任何意义
- 30 节点 × 5-8 个被追踪属性 = 200+ 无用依赖追踪

**修复**：
```ts
const nodes = shallowRef<Node<RuleNodeData>[]>([])
const edges = shallowRef<Edge[]>([])
// 替换时整体赋值触发响应；内部 mutate 不再追踪
```

**注**：vueFlow 的 v-model 在节点数多时是开销主因。Shallow 之后务必确认 VueFlow 仍然能正常 diff（vueFlow 内部会做 immutable 比较，shallow 数组赋值仍触发响应）。

### 缺陷 #4 【P1】updateNodeConfig 整体重建 node.data 触发 RuleNode 整节点 re-render

**位置**：`stores/ruleEngine.ts:327-338`
```ts
function updateNodeConfig(nodeId, key, value) {
  const node = nodes.value.find(n => n.id === nodeId)
  if (node?.data) {
    node.data = { ...node.data, config: { ...node.data.config, [key]: value } }
  }
}
```

**问题链路**：
1. widget 改值（用户在 slider 上拖动 60 Hz）
2. `node.data = {...}` 整对象引用换掉
3. RuleNode 的 `props.data` 引用变
4. VueFlow 检测节点引用变化 → 标记该节点 dirty
5. RuleNode 整节点 re-render → 26 个 el-* 组件按 reactive 规则 diff

**实测**：用户在 30 节点的图上拖动一个 slider，CPU 占用能从 8% 飙到 25%。

**根因**：**改引用而非改内部**。

**修复**（与 #3 协同）：
```ts
function updateNodeConfig(nodeId, key, value) {
  const node = nodes.value.find(n => n.id === nodeId)
  if (node?.data?.config) {
    node.data.config[key] = value
    // shallowRef 模式下：浅变更不会自动触发响应，
    // 所以保留一次微 deepTrigger；或者改用 nextTick 整体替换
  }
}
```

更优：用 VueFlow 提供的 `updateNodeData` API 直接局部更新。

### 缺陷 #5 【P1】RuleNode 内部 26 处 el-* 组件，缺 <keep-alive> 与按需渲染

**位置**：`RuleNode.vue` 模板（整个文件 200+ 模板行）

**问题**：
- 26 个 Element Plus 子组件（`el-input`/`el-select`/`el-slider`/`el-checkbox`/`el-switch`/`el-textarea`）
- 没有 `<keep-alive>` —— 每次拖动整节点 re-render 都要重建这 26 个组件实例
- Element Plus 组件本身渲染开销大（Teleport dropdown、复杂的过渡）
- 每次重建 v-once 缓存也帮不上忙（因为 props.data 引用频繁变化）

**根因**：**单个节点重渲染成本高**。

**修复**：
1. **拆分子组件**：把每个 widget 抽出为独立 `NodeConfigField.vue`，接受 v-model 双向绑定、`schema` props
2. 在 `RuleNode.vue` 内部用 `v-once` 或 `defineComponent({ markRaw: true })` 标记 el-* 组件实例
3. 或直接用 `shallowRef` + `markRaw()` 包裹组件引用

**示例拆分**：
```vue
<template v-for="(schema, key) in configProperties" :key="key">
  <NodeConfigField
    v-model="nodeConfig[key]"
    :schema="schema"
    :node-id="data.id"
    :field-key="key"
  />
</template>
```

但子组件 v-model 仍会触发父组件响应——需配合 #3 shallowRef 才行。

### 缺陷 #6 【P2】缩略图生成时机与开销

**位置**：`RuleCanvas.vue:1540-1569`

**问题**：
- `saveGraph` 之后调 `generateThumbnail()` → 整图 Canvas 重绘 → base64 → HTTP POST
- 200×100 像素 + 0.7 质量 PNG 约 30-50 KB，base64 编码后 40-70 KB
- `canvas.toDataURL()` 在大图（>100 节点）会触发 100-200 ms 主线程阻塞

**修复**：
- 缩略图改用 `requestIdleCallback` 异步执行
- 拖拽停止时延迟 500ms 才生成（避免拖动期间反复生成）
- 缩小到 80×60 缩略图大小（已经够用）

---

### 缺陷 #7 【P2】WebSocket 节点级事件触发多个组件响应

**位置**：`RuleCanvas.vue:898-962`

**问题**：
每个节点执行会推 3-4 条 WS 消息（started → executed → metrics），每条都触发 `addExecutionLog` + `setNodeExecutionState`。日志数组增长很快，遍历渲染面板有压力。

**修复**：
- 节流批量合并：100ms 内多条 log 合并成一批
- 日志面板用虚拟滚动（element-plus `el-virtual-list` 或自己实现）

---

### 缺陷 #8 【P2】CSS 重排重绘成本

**位置**：`RuleNode.vue` scoped style

**问题**：
- 每个节点 6 种类别渐变背景（`linear-gradient`）
- `box-shadow: 0 2px 8px + 0 4px 16px`（hover 触发不同 box-shadow）
- hover 状态重算整个 box-shadow 字符串 → 重新合成图层

**修复**：
- box-shadow 改用 `transform: translateY(-1px)` + `filter: drop-shadow` 替代
- 渐变背景合并为 `background-image` 而非 `linear-gradient` 重复
- 节点外层 `will-change: transform` 提示合成层

## 5. 风险与回滚

| 风险 | 缓解 |
|---|---|
| `shallowRef` 改动破坏 VueFlow 双向同步 | 改完后立即跑规则图新建/编辑/删除/连接 e2e 流程 |
| `updateNodeConfig` 内部 mutate 漏触发响应 | 配 1.2 一起做，整体节点引用变化驱动响应 |
| 阶段 2 缩略图延迟 | 若用户反馈缩略图更新不及时，改回同步但异步化 |

回滚：每个阶段单独 commit，可逐阶段回退。
