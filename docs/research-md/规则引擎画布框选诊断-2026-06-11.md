## 1. 当前实现概览（Phase 17.5）

### 1.1 设计目标

老大反馈"框选过程中卡顿"。Phase 17.5 的修复策略 B（"画框不卡"）：

- **mousemove 期间不计算命中**：把 `userSelectionRect.value = null`，让 VueFlow 内部 `Pane.onPointerMove` 第一行 `if (!userSelectionRect.value) return` 直接返回，跳过 60Hz × O(N) 的 `getNodesInside`
- **自己接管框的可视层**：用 `customSelectionRect` ref 在 `.flow-container` 内画一个 `<div>`，mousemove 时只改 CSS `left/top/width/height`
- **mouseup 时一次性算命中**：`@selection-end` 触发时调 `getNodesInside` + `addSelectedNodes`，走完整 vue-flow 选中链路

## 2. VueFlow 内部坐标系约定（重要前置知识）

要理解 §3 的 bug，必须先掌握 VueFlow 三个坐标系：

| 坐标系 | 单位 | 来源 | 例子 |
|---|---|---|---|
| **屏幕坐标 (client)** | px | 浏览器视口左上角为 (0,0) | `event.clientX/Y`、`getBoundingClientRect()` |
| **容器坐标 (pane-relative)** | px | `vueFlowRef` 元素左上角为 (0,0)，即 `client - containerBounds.left/top` | `Pane.getMousePosition(event, containerBounds)` |
| **画布坐标 (flow / renderer)** | px (除以 zoom) | 画布原点（节点 `position` 字段所用）；`容器坐标 = 画布坐标 × zoom + viewport.x` | `node.position`、`node.computedPosition` |

### 2.1 `getNodesInside` 的输入语义

```js
// vue-flow-core.mjs:3735
function getNodesInside(nodes, rect, viewport, partially = false, excludeNonSelectableNodes = false) {
  const paneRect = {
    ...pointToRendererPoint(rect, viewport),    // 把 rect.{x, y} 反变换到画布坐标
    width:  rect.width  / viewport.zoom,
    height: rect.height / viewport.zoom
  };
  // ↑ 与 nodeToRect(node)（node.computedPosition + dimensions）即画布坐标比对
}

// vue-flow-core.mjs:3682
function pointToRendererPoint({ x, y }, { x: tx, y: ty, zoom: tScale }) {
  return { x: (x - tx) / tScale, y: (y - ty) / tScale };
}
```

`viewport.x/y` 是 `.vue-flow__transformationpane` 的 CSS translate offset，**含义是**「容器原点 → 画布原点」的位移（容器坐标系下）。

→ 因此 `pointToRendererPoint` 假设输入 `rect.{x,y}` 是 **容器坐标**，输出是画布坐标。

### 2.2 VueFlow 内部如何调用 `getNodesInside`

```js
// vue-flow-core.mjs:8285（onPointerDown 内部）
const { x, y } = getMousePosition(event, containerBounds.value);
//                              ↑ event.clientX - containerBounds.left
userSelectionRect.value = { x, y, startX: x, startY: y, … };

// vue-flow-core.mjs:8318（onPointerMove 内部）
selectedNodeIds.value = new Set(
  getNodesInside(nodes.value, nextUserSelectRect, viewport.value, …).map(n => n.id)
);
```

**关键事实**: VueFlow 内部传给 `getNodesInside` 的 rect 永远是 **容器坐标**（已减过 `containerBounds.left/top`）。

## 3. Bug 列表（按严重度排序）

### 🔴 BUG-1【严重·影响命中正确性】坐标系混用：`getNodesInside` 输入用绝对屏幕坐标

**位置**: `RuleCanvas.vue:1411–1449`

```ts
function handleSelectionEnd(event: any) {
  …
  const start = selectionStartPos      // ⚠ {x: event.clientX, y: event.clientY}
  const end   = lastMousePos.value      // ⚠ {x: event.clientX, y: event.clientY}

  const finalRect = {
    x: Math.min(start.x, end.x),        // ⚠ 绝对屏幕坐标
    y: Math.min(start.y, end.y),
    width:  Math.abs(end.x - start.x),
    height: Math.abs(end.y - start.y),
    startX: start.x,                    // ⚠ 绝对屏幕坐标
    startY: start.y
  }

  const hitNodes = getNodesInside(
    nodes.value as any[],
    finalRect,                          // ⚠ 期望「容器坐标」，实际传入「屏幕坐标」
    viewport,
    SelectionMode.Partial === SelectionMode.Partial,
    true
  )
  …
}
```

**根因**: `selectionStartPos` 在 `handleSelectionStart` 里直接 `{x: event.clientX, y: event.clientY}`（行 1359-1364），而 `lastMousePos` 在 `handleCanvasMouseMove` 里也是 `{x: event.clientX, y: event.clientY}`（行 1978）。两者都是**绝对屏幕坐标**，没有减去 `vueFlowRef.getBoundingClientRect().{left, top}`。

`getNodesInside` 内部把 rect 看作「容器坐标」做 `pointToRendererPoint(rect, viewport)`，得到的"画布坐标"会**整体偏移** `containerBounds.left/top` 个屏幕像素 ÷ zoom。

**实际影响**:
- 左侧 palette 默认展开 280px → 框选向右偏移 ~280/zoom 个画布单位
- 顶部工具栏占若干 px → 框选向下偏移 ~Y/zoom 个画布单位
- 现象: 用户在画布**左上角**框选，命中的却是中右部位置的节点；在视口外（理论上 finalRect 越界）的虚拟区域才能"命中"应有节点
- 当 zoom 较小（0.3）时偏移在画布坐标上更大（~933px），错位非常明显

**复现路径**:
1. 打开规则画布，确保左侧 palette 展开
2. 在视口最左上角附近尝试框选最左上角的节点
3. 观察：节点不会被选中，反而是右下方的节点被选中

**修复方向**: 在所有进入 `finalRect` 的坐标点上减去 `vueFlowRef.getBoundingClientRect().{left, top}`，转成容器坐标。或者改为用 `screenToFlowCoordinate(event)` 直接拿画布坐标，自己写一个 nodeRect ↔ flowRect 的相交判定（绕过 `getNodesInside` 的 viewport 反变换）。

### 🔴 BUG-2【严重·影响视觉位置】自绘选区框定位错位

**位置**: `RuleCanvas.vue:426–435, 1367, 1971–1976`

```html
<!-- 模板 -->
<div
  v-if="customSelectionRect"
  class="custom-selection-rect"
  :style="{
    left:   customSelectionRect.x      + 'px',     ⚠ 绝对屏幕坐标
    top:    customSelectionRect.y      + 'px',
    width:  customSelectionRect.width  + 'px',
    height: customSelectionRect.height + 'px'
  }"
/>
```

```scss
/* line 3121 */
.custom-selection-rect {
  position: absolute;       /* ← 相对最近的 position:relative/absolute/fixed 父级 */
  …
}
```

**根因**:
- `<div class="custom-selection-rect">` 的 DOM 父级是 `.flow-container`（行 360, `position: relative`）
- CSS `position: absolute` + `left/top` 相对 `.flow-container` 内坐标系（即「容器坐标」）
- 但 `customSelectionRect.x/y` 写入的是 `event.clientX/Y` **绝对屏幕坐标**

**实际影响**:
- 用户拖动鼠标时，框始终偏移到鼠标右下方（偏移量 = `flow-container.getBoundingClientRect().left/top`）
- 由于 BUG-1 中的命中算法**也**用相同的绝对坐标，框可视位置和命中区域**碰巧一致**（两者偏移方向相同）
- 但用户视觉上看到的是：框跟在鼠标位置，但框的位置远离当前鼠标 ~280px。鼠标和"看上去要框的节点"的几何关系完全错乱
- 当 palette 折叠时偏移变小（仍非 0，因为顶部还有工具栏），用户看到框选起点跳变

**修复方向**: 与 BUG-1 同源；写入 customSelectionRect 之前先减 `flow-container.getBoundingClientRect().{left, top}`，让坐标变成容器坐标。

### 🟠 BUG-3【中等·影响选中状态一致性】重复框选时旧选中残留

**位置**: 跨多处 — `RuleCanvas.vue:1815, 1349, 1815-1846`

**根因链**:

1. 用户第一次框选完毕，store.nodes[].selected = true 已写入若干节点
2. 用户在空白处再次按下鼠标准备第二次框选
3. VueFlow `Pane.onPointerDown` 调 `removeSelectedElements()`（清旧选中），它会触发 `nodesChange` emit `[{type:'select', selected:false}, …]`
4. **但**接着 `emits.selectionStart(event)` 同步执行 → `handleSelectionStart` 把 `isSelectionDragging.value = true` 和 `isBatchDragging.value = true`
5. 实际上 `removeSelectedElements()` 是在 `selectionStart` 之**前**同步触发的，所以这一步的 select changes 会**正常处理**（isBatchDragging/isSelectionDragging 此刻仍是 false） — 这一步本身没问题
6. **真正的问题**：当框选过程中 VueFlow 内部 `selectedNodeIds` 实际上**不会变**（因为 userSelectionRect 已被我们设为 null，onPointerMove 直接 return），所以 `selectedNodeIds.size` 在 selectionEnd 时**还是 0**
7. 在 `handleSelectionEnd` 里，`addSelectedNodes(hitNodes)` 只追加新命中节点 → vue-flow 把它们标记为 selected → emit nodesChange[select:true]×K

但是：**vue-flow 的 selected nodes 集合并没有"先清旧的"动作**，因为 vue-flow 以为 selectedNodeIds 是空的（onPointerMove 没跑过）。所以如果某次 onPointerDown 之前有节点 selected=true 在 store 里但 vue-flow 内部 selectedNodeIds 已被清，vue-flow 不会触发 select=false 给那些"已清"的节点。

**实际影响**: 在多数场景由 onPointerDown 触发的 `removeSelectedElements()` 已经把旧选中清掉了，本 bug 不会显形。但当选中状态以其他路径写入（例如用户键盘 Ctrl+A 后框选另一组），vue-flow 内部和 store.nodes 之间可能短暂不一致。这是低频但存在的 race。

**修复方向**: 在 `handleSelectionEnd` 进入 `addSelectedNodes` 之前，主动调一次 `removeSelectedElements()`，或者改用 `syncSelectionToStoreNodes` 显式同步（见 BUG-7）。

### 🟠 BUG-4【中等·性能回退】`addSelectedNodes` 走全量重渲染路径

**位置**: `RuleCanvas.vue:1455`

```ts
addSelectedNodes(hitNodes as any)   // 触发 @nodes-change emit, 走 applyVueFlowNodeChanges
```

`addSelectedNodes` 内部 emit `nodesChange[{type:'select', selected:true}, …]` × K → 项目 `handleNodesChange`（行 1815）把它们塞进 `meaningful: any[]` → 走 `applyVueFlowNodeChanges(meaningful)` → 替换 `store.nodes` 数组引用 → VueFlow `useVModel` 浅 watch 检测到引用变化 → **整图 N 节点 vdom diff/patch**。

注意：本文件已经实现了 §1.2 的 `syncSelectionToStoreNodes`（行 1477，原地变异 + triggerRef，引用不变 → vdom 跳过），但 Phase 17.5 没用它，注释里说"上一版 P0-B 的 triggerRef 路径保留" — 实际等于 **回退** 到 vdom diff 路径。

**实际影响**: 每次框选结束，整图 N 节点 vdom diff（80 节点 ≈ 5–15ms），把"画框不卡"的优化在 mouseup 这帧重新付出代价。这与 Phase 17.5 的设计原则矛盾。

**修复方向**: 用 `syncSelectionToStoreNodes(selectedIds)` 替代 `addSelectedNodes`，并配套调一次 vue-flow 的内部 selected 同步（详见 §5.2）。

### 🟡 BUG-5【低·死代码】`lastUserSelectionRect` watch 已无用

**位置**: `RuleCanvas.vue:1340–1346`

```ts
let lastUserSelectionRect: { x: …; startX?: …; startY?: … } | null = null
watch(userSelectionRect, (rect) => {
  if (rect) {
    lastUserSelectionRect = rect as any
  }
})
```

**根因**:
- Phase 17.5 在 `handleSelectionStart` 中把 `userSelectionRect.value = null`
- VueFlow 的 onPointerMove 也因为 userSelectionRect 为 null 直接 return，**不再写 userSelectionRect**
- → watch 实际**永远不再被触发**（除了 selectionStart 时 vue-flow 内部赋值的那一瞬，立刻被我们设回 null）
- 即使 watch 触发，`handleSelectionEnd` 内**没有任何代码读取** `lastUserSelectionRect`，仅有 4 处赋值 null
- 注释 1338 行已自承：「当前实现 cachedSelectionRect 只用于诊断, 实际逻辑不再读它」

**实际影响**:
- 占用一个 watch effect 注册 + 1 个闭包变量
- 干扰阅读：5 处 `lastUserSelectionRect = null` 让人误以为它有意义
- 性能影响 ≈ 0，但会误导后续维护者

**修复方向**: 直接删除 watch + `lastUserSelectionRect` 变量。

### 🟢 BUG-9【提示·非 bug】`isSelectionDragging` flag 现已无价值

**位置**: `RuleCanvas.vue:1798, 1836, 1350`

`handleNodesChange` 里 `if (c.type === 'select' && isSelectionDragging.value) continue` 历史用途是过滤 mousemove 期间 vue-flow 内部产生的 select changes。Phase 17.5 后 vue-flow 内部 onPointerMove 已不跑（userSelectionRect=null），不会再 emit select changes。

**修复方向**: 谨慎评估是否还有其他写 select change 的路径（例如用户 Shift+click 多选）。如果只有框选会写，flag 可删；否则保留。

## 4. 性能现状评估

### 4.1 分阶段开销

测试假设：80 节点、4K 屏、Chrome 120、笔记本中端 GPU。

| 阶段 | 实际开销 | 理论下界 | 状态 |
|---|---|---|---|
| **mousedown** (selectionStart) | `removeSelectedElements()` × N=80 节点 emit ≈ 1–2ms | O(K_old)，K_old=旧选中数 | 🟡 全量清，可优化但低频 |
| **mousemove × 60Hz** | `handleCanvasMouseMove` ~0.05ms + DOM patch ~0.1ms ≈ **0.15ms/帧** | ≈ 0.15ms/帧（CSS 直写不可再省） | ✅ 已是最优 |
| **mouseup** (selectionEnd) | `getNodesInside` ~0.5ms + `addSelectedNodes` → `applyVueFlowNodeChanges` 全量 vdom diff **5–15ms** | O(N) once + 原地变异 ~1ms | 🔴 **退化**：本应走 syncSelectionToStoreNodes |
| **mouseup 后渲染** | 80 节点 wrapper 触发 selected class 变化 → CSS outline 切换（已用 `outline` 替代 border-width，无 layout） | 同左 | ✅ CSS 已最优 |

### 4.2 总体评估

- **mousemove 流程**：Phase 17.5 「自绘框 + userSelectionRect=null」是当前最优解 ✅
- **mouseup 流程**：现实现把 Phase 17.5 的优化在 mouseup 这帧用 `addSelectedNodes` 全量 vdom 还了回去 🔴

→ 「框选过程不卡」目标达成；「框选结束不卡」未达成（5–15ms 单帧 spike）。

### 4.3 与 BUG-1/BUG-2 的关系

性能优化都建立在「命中正确性」之上。当前 BUG-1 让 `getNodesInside` 计算结果错误，导致 `addSelectedNodes` 的 K（命中数）也是错的。性能数据需要在修完坐标系 bug 后重新跑基线。

### 4.4 是否「性能最优」

**结论：不是最优**，主要差距：

1. ❌ mouseup 走全量 vdom diff（应改为原地变异 + triggerRef）
2. 🟡 命中算法 `getNodesInside` 是 O(N) 线性扫，对 80 节点足够（<0.5ms），但 N>1000 时应引入空间索引（quadtree / R-tree）—— 当前规模不需要
3. 🟡 mousedown 时 `removeSelectedElements` 全量清，可优化为只清「即将被新框选取代之外」的节点 —— 但通常 K_old 较小，收益有限

详见 §5.2。

## 5. 修复方案与最优实现路径

### 5.1 BUG-1 / BUG-2 修复（坐标系）

**方案 A：减容器偏移（最小改动）**

```ts
// 1) 在 handleSelectionStart 改：
function handleSelectionStart(event: any) {
  isSelectionDragging.value = true
  isBatchDragging.value = true
  store.setSelectionBoxActive(true)

  const bounds = flowContainer.value?.getBoundingClientRect()  // 新增
  const offsetX = bounds?.left ?? 0
  const offsetY = bounds?.top  ?? 0

  if (event && event.clientX !== undefined) {
    selectionStartPos = { x: event.clientX - offsetX, y: event.clientY - offsetY }  // 容器坐标
  } else {
    const lp = lastMousePos.value
    selectionStartPos = lp ? { x: lp.x - offsetX, y: lp.y - offsetY } : { x: 0, y: 0 }
  }
  userSelectionRect.value = null
  customSelectionRect.value = { x: selectionStartPos.x, y: selectionStartPos.y, width: 0, height: 0 }
}

// 2) 在 handleCanvasMouseMove 改：
function handleCanvasMouseMove(event: MouseEvent) {
  if (isSelectionDragging.value && selectionStartPos) {
    const bounds = flowContainer.value?.getBoundingClientRect()
    const cx = event.clientX - (bounds?.left ?? 0)
    const cy = event.clientY - (bounds?.top  ?? 0)
    const sx = selectionStartPos.x
    const sy = selectionStartPos.y
    customSelectionRect.value = {
      x: Math.min(sx, cx),
      y: Math.min(sy, cy),
      width:  Math.abs(cx - sx),
      height: Math.abs(cy - sy)
    }
    lastMousePos.value = { x: cx, y: cy }   // 注：lastMousePos 现在也是容器坐标
    return
  }
  …
}

// 3) handleSelectionEnd 不需要改，因为 selectionStartPos 和 lastMousePos 都已转好。
//    但要提防：lastMousePos 在 panning 路径里仍然写绝对坐标（line 1985）
//    → 要么把所有路径统一为容器坐标，要么再拆一个 lastSelectionMousePos 状态
```

**注意**: `lastMousePos` 当前在多个路径混用（panning、剪贴板 mousePos、quickAdd 等）。建议**新增一个独立的 `selectionLastMousePos`**，避免干扰其他路径。

**方案 B：不用 `getNodesInside`，自己写画布坐标 nodeRect 比对（更可控）**

```ts
function handleSelectionEnd(event: any) {
  …
  // 用 screenToFlowCoordinate 把屏幕坐标点转成画布坐标
  const flowStart = screenToFlowCoordinate({ x: start.x, y: start.y })
  const flowEnd   = screenToFlowCoordinate({ x: end.x,   y: end.y   })
  const flowRect = {
    x: Math.min(flowStart.x, flowEnd.x),
    y: Math.min(flowStart.y, flowEnd.y),
    x2: Math.max(flowStart.x, flowEnd.x),
    y2: Math.max(flowStart.y, flowEnd.y)
  }

  // 自己 O(N) 扫一遍，全在画布坐标系做比较
  const hitIds = new Set<string>()
  for (const n of nodes.value as any[]) {
    if (n.hidden) continue
    const w = n.dimensions?.width  ?? 200
    const h = n.dimensions?.height ?? 80
    const nx = n.position.x, ny = n.position.y
    // partial 模式：相交即命中
    const overlaps = nx + w > flowRect.x && nx < flowRect.x2 &&
                     ny + h > flowRect.y && ny < flowRect.y2
    if (overlaps) hitIds.add(n.id)
  }
  syncSelectionToStoreNodes(hitIds)   // 不走 vdom diff，顺便修 BUG-4
  …
}
```

**优点**: 完全独立于 vue-flow 内部坐标系实现，未来 vue-flow 升级若改了 `pointToRendererPoint` 也不会受影响。

**推荐**: 方案 B（更解耦），但需要补一步「让 vue-flow 内部 selectedNodeIds 也同步」。见 §5.2。

### 5.2 BUG-4 修复（mouseup 性能回退）

让 store.nodes 选中态用 syncSelectionToStoreNodes（轻量）+ vue-flow 内部 selectedNodeIds 用 addSelectedElements（让 .selected class 上去）。

```ts
// 在 handleSelectionEnd 内：
syncSelectionToStoreNodes(hitIds)               // store 路径：原地变异 + triggerRef，引用不变
// vue-flow 内部要让 .selected class 渲染。两条路：
// (a) 直接 mutate findNode(id).selected = true  → 不会触发 nodesChange，但视觉同步
// (b) 调 addSelectedNodes(...) 但配置 isBatchDragging.value = true 跳过 handleNodesChange 的全量 diff
```

**推荐 (a)**：用 `findNode(id)` 拿到 vue-flow 内部 GraphNode，原地写 `.selected`，不走 emit 链路，最低开销。

**注意**: vue-flow 节点 `.selected` 视觉是由 NodeWrapper 读取 GraphNode.selected 决定（参考 vue-flow-core.mjs:NodeWrapper），所以原地写 GraphNode.selected 后还需要 `triggerRef` 或单节点级别的更新机制。需要 PoC 验证。

### 5.4 BUG-3 修复（重复框选状态）

显式同步：

```ts
function handleSelectionEnd(event: any) {
```

## 8. 一句话结论

> 当前框选实现 **mousemove 流程** 已是性能最优（自绘框 + 阻断 vue-flow Pane 内部 onPointerMove），但存在 **2 个严重坐标系 bug**（命中区错位 + 自绘框视觉错位）和 **1 个性能回退**（mouseup 走全量 vdom diff）。
>
> 修复优先级：BUG-1/BUG-2 同源同步修（§5.1 方案 B 推荐）→ BUG-4 改走 `syncSelectionToStoreNodes`（§5.2）→ 清理死代码与 DEBUG 日志（§5.3）。

## 附：坐标系速查表

| 量 | 单位 | 例 |
|---|---|---|
| `event.clientX/Y` | 屏幕 px | 鼠标 → 视口左上原点 |
| `containerBounds = vueFlowRef.getBoundingClientRect()` | 屏幕 px | 容器盒 |
| `getMousePosition(event, containerBounds)` | 容器 px | `clientX - bounds.left` |
| `userSelectionRect` (vue-flow 内部) | 容器 px | 由 getMousePosition 得到 |
| `viewport = { x, y, zoom }` | 容器 px / 倍率 | `.vue-flow__transformationpane` translate |
| `pointToRendererPoint(p, viewport)` | 画布 px | `(容器px - viewport.x) / zoom` |
| `node.position` | 画布 px | 用户存的逻辑坐标 |
| `node.computedPosition` | 画布 px | parent-relative 计算后的 |
| `node.dimensions.{width, height}` | 画布 px / 屏幕 px? | **存疑**：实测 dimensions 来自 `el.offsetWidth`，是布局像素（屏幕 px），但 nodeToRect 把它和 computedPosition（画布 px）混在一起。vue-flow 内部当作画布 px 用，故而**只有 zoom=1 时严格正确**。这是 vue-flow 的已知简化。 |

> **dimensions 单位混用**: 这个是 vue-flow 内部就存在的小问题，不是项目代码引入的。在 zoom != 1 时 `getNodesInside` 命中边界会有 1% 量级误差，对 partial 模式影响可忽略。
