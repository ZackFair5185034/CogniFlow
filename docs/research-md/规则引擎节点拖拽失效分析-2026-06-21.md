# 规则引擎节点拖拽失效分析 (2026-06-21)

> 静态代码分析报告。问题现象：从左侧节点列表拖拽节点到画布后，新增节点无法被拖拽。

## 1. 问题背景

- 分支：`feature/rule-engine-lightweight-nodes`
- 最近提交：`3c8b97ba feat(rule-engine): 画布交互能力迭代 (P0/P1/P2 共 10 项)`
- 工作区有未提交修改：`webui/src/composables/useCogniFlowDrag.ts`
- 用户反馈：从节点列表拖拽到画布上的"新增节点"不能被拖拽

## 2. 拖拽机制梳理

规则引擎画布存在**两套独立的拖拽机制**，需分别分析：

| 机制 | 用途 | 技术栈 | 关键文件 |
|------|------|--------|----------|
| **A. 调色板 → 画布** | 从左侧节点库拖入画布创建节点 | HTML5 Drag & Drop API | `RuleCanvas.vue` |
| **B. 画布内移动** | 移动画布上已有节点的位置 | d3-drag (自研接管) | `useCogniFlowDrag.ts` |

用户"从节点列表拖拽到画布"= 机制 A 创建节点；"新增节点不能被拖拽"= 机制 A 创建的节点在机制 B 中无法移动。

## 3. 机制 A：调色板 → 画布 (HTML5 DnD)

### 3.1 代码链路

```
.node-item[draggable="true"] @dragstart → handleDragStart()
  ↓ setData('application/node-type', JSON.stringify(nodeDef))
.flow-container @dragover.prevent @dragenter.prevent @drop → handleDrop()
  ↓ getData + screenToFlowCoordinate + snapGrid
store.createNode(nodeDef, position)
  ↓ nodes.value = [...nodes.value, markRaw(newNode)]
VueFlow 渲染 .vue-flow__node[data-id]
```

### 3.2 静态分析结论

- `handleDragStart` / `handleDrop` 逻辑正确，`createNode` 始终返回 `true`
- VueFlow fork（`/home/wanglei/vue-flow/packages/core`）的 `Pane.vue` / `Viewport.vue` / `VueFlow.vue` **均未注册 `@dragover`/`@drop`/`stopPropagation`**，不会拦截冒泡到 `.flow-container` 的拖拽事件
- `.flow-container` 的 `@dragover.prevent` 在事件冒泡阶段调用 `preventDefault()`，浏览器允许 drop
- `.empty-state` / `.custom-selection-rect` / `.selection-mode-hint` 均 `pointer-events: none`，不阻断 drop

**结论：机制 A 代码正确，节点能成功创建到画布。** 真正失效的是机制 B（节点落画布后无法移动）。

## 4. 机制 B：画布内移动 (d3-drag) — 根因所在

### 4.1 d3-drag filter 的事件对象问题

`useCogniFlowDrag.ts` 在 `.vue-flow__viewport` 上挂单一 d3-drag handler（事件委托），其 `filter` 决定是否启动拖拽。

**已提交版本 (3c8b97ba) 的 filter：**
```javascript
.filter((event: MouseEvent) => {
  if (event.button) return false
  const target = event.target as HTMLElement | null       // ← 直接用 event.target
  if (!target) return false
  const nodeEl = target.closest<HTMLElement>('.vue-flow__node[data-id]')
  if (!nodeEl) return false
  if (!target.closest('.node-header')) return false         // ← 限制只能从标题栏拖
  ...
  ;(event as any).__cfNodeEl = nodeEl
  return true
})
```

**工作区修复版的 filter：**
```javascript
.filter((event: any) => {
  const srcEvent = event?.sourceEvent ?? event              // ← 兼容 raw MouseEvent / D3 DragEvent
  if (srcEvent.button) return false
  const target = srcEvent.target as HTMLElement | null
  if (!target || typeof target.closest !== 'function') return false   // ← 防御性校验
  const nodeEl = target.closest('.vue-flow__node[data-id]') as HTMLElement | null
  if (!nodeEl) return false
  if (!target.closest('.node-header')) return false
  ...
  srcEvent.__cfNodeEl = nodeEl
  return true
})
```

### 4.2 d3-drag v3.0.0 源码验证

查阅 `node_modules/d3-drag/src/drag.js`（v3.0.0）：

```javascript
function drag(selection) {
  selection.on("mousedown.drag", mousedowned)   // ← mousedown 监听
}
function mousedowned(event, d) {
  if (touchending || !filter.call(this, event, d)) return;   // ← filter 收到原生 MouseEvent
  ...
  nodrag(event.view);      // 临时屏蔽 window 的 dragstart（防 HTML5 DnD 串扰）
  nopropagation(event);
  gesture("start", event); // ← start 收到 D3 DragEvent，其 sourceEvent = 同一原生 MouseEvent
}
```

- **filter 阶段**：`event` 是 d3-selection 透传的**原生 MouseEvent**，`event.target` 即鼠标下方的真实 DOM 元素
- **start 阶段**：`event` 是 d3 构造的 **D3 DragEvent**，`event.sourceEvent` 指向 filter 阶段的同一原生 MouseEvent

因此 `__cfNodeEl` 写在原生 MouseEvent 上、start 从 `event.sourceEvent` 读，对象引用一致，数据传递正确。**已提交版本的 filter 在 d3-drag v3.0.0 下理论上可工作。**

### 4.3 实际失效原因推断

工作区修复注释明确记录了症状：
> 之前的代码假设了 sourceEvent, 结果 event.target 是 d3 内部对象, .closest() 永远返回 null, filter 永远 reject, **拖动功能彻底失效 (新建节点 + 已有节点都无法拖)**。

结合运行时实际表现（节点无法移动），推断存在以下一种或多种情况导致 filter 实际 reject：

1. **d3-selection 事件透传层在运行时对 `event` 做了包装**，使 filter 收到的 `event.target` 并非真实 DOM 元素（与源码静态阅读结论相悖的运行时行为）
2. **`.node-header` 限制 (3c8b97ba 新增)**：拖拽只能在节点标题栏触发。若用户拖拽节点**主体区域（配置区/端口区）**，`target.closest('.node-header')` 返回 null，filter reject → 节点不动。这是体感上"新增节点不能拖"的最直接原因
3. 已提交 filter 缺少 `typeof target.closest !== 'function'` 防御，若 `target` 为非 Element 节点会抛错中断

### 4.4 关键证据：`.node-header` 限制是体感主因

`RuleNode.vue` 中节点结构：
```html
<div class="rule-node">
  <div class="node-header">  ← 仅此区域可拖 (占节点顶部 ~30px)
    <div class="node-icon">...</div>
    <div class="node-title">...</div>
    <button class="node-collapse-btn">...</button>
  </div>
  <div class="node-ports">...</div>          ← 不可拖 (cursor: default)
  <div class="node-config-section">...</div> ← 不可拖 (mousedown.stop + cursor: text)
</div>
```

新增节点默认**全展开 (LOD 1, 280px)**，配置区占节点大部分面积。用户自然地抓节点中部/下部拖动 → 命中 `.node-config-section` 或 `.node-ports` → filter reject → 节点纹丝不动 → "新增节点不能拖拽"。

而已有节点（加载自保存图）若处于折叠态（`.expanded` 类，200px，隐藏配置区），标题栏占比更大，更易被命中，因此体感上"老节点能拖、新节点不能拖"。

## 5. d3-drag 与 HTML5 DnD 串扰排查

担心 d3-drag 的 `nodrag()` 会持久屏蔽 HTML5 dragstart 导致机制 A 也失效，核查如下：

- `nodrag(event.view)` 在 `mousedowned` 中**filter 通过后**才调用，给 window 挂 `dragstart.drag = noevent`（preventDefault + stopPropagation）
- `yesdrag(event.view)` 在 `mouseupped` 中移除该监听
- `mouseup.drag` 监听在 `nodrag` **之前**注册，即使 `gesture("start")` 抛错，mouseup 仍会触发 `yesdrag` 解除屏蔽
- 调色板 `.node-item` 的 mousedown 冒泡路径是 `.node-palette → .canvas-body`，**不经过** `.vue-flow__viewport`，d3-drag 监听器不会触发

**结论：d3-drag 不会持久阻断机制 A。** 两套机制隔离良好。

## 6. 根因总结

| # | 因素 | 影响 | 状态 |
|---|------|------|------|
| 1 | **`.node-header` 限制** (3c8b97ba) | 节点仅标题栏可拖，新增节点全展开配置区占大面积，用户抓主体拖不动 | **体感主因** |
| 2 | **d3-drag filter 事件对象** | 已提交版本在运行时可能因 event 包装导致 filter 永久 reject | 工作区已修（防御性 `srcEvent = event?.sourceEvent ?? event`） |
| 3 | 缺少 `target.closest` 类型防御 | target 非 Element 时抛错 | 工作区已修 |

## 7. 修复建议

### 7.1 已有修复（工作区，待提交）
`useCogniFlowDrag.ts` 的 filter 改为防御性写法，兼容 raw MouseEvent / D3 DragEvent 两种入参，并校验 `target.closest` 可调用性。**建议保留并提交。**

### 7.2 待评估的 UX 改进
`.node-header` 限制使新增节点（默认全展开）体感难拖，可选方案：
- **方案 A（保持限制）**：在节点标题栏增加视觉提示（如 `cursor: grab` + 拖拽手柄图标），引导用户抓标题栏
- **方案 B（放宽限制）**：允许 `.node-ports` 也参与拖拽（配置区仍 `.mousedown.stop` 排除），增大可拖命中区
- **方案 C（恢复旧行为）**：移除 `.node-header` 限制，整个节点壳可拖（牺牲"端口/配置区独立交互"的分区 cursor 设计）

> 当前 `RuleNode.vue` 注释明确"用户反馈不喜欢小手样式"，cursor 全为 default，缺乏可拖区域的视觉引导，放大了方案 A 的体感问题。
